Architecture field guide · 22 Oct 2026

One runtime owns the work.
Interfaces come and go.

Raphie is a headless Bun runtime. Web and Discord submit commands and observe results; execution, approvals and history stay in one durable place.

Delivered

Web client host

React with TanStack Start, Router and Query. A view onto the runtime, never its owner.

  • Opens no runtime database and runs no models.
  • Reads focused queries; subscribes to one session's SSE.
  • Switches backends without a page reload.
  • Drafts are scoped by backend and session.

Delivered · optional

Discord adapter

A messaging channel. Native messages and approval buttons; no inspector required.

  • Verifies configured owner, guild, channel and thread.
  • Never accepts a session ID from message text.
  • One scoped delivery worker renders chunks, cards and edits.
  • Disabled by configuration unless enabled.

Future

Desktop, CLI, Telegram

Later clients use the same operations. None gets a second executor or direct database access.

  • Closing a desktop or CLI view must not cancel work.
  • Remote clients need authenticated access first.
  • Cross-channel continuation will be explicit, not implicit.

touches → operations (when built)

Delivered

Trusted ingress

Adapters establish who is speaking. The runtime issues the actor context; callers cannot claim one.

  • HTTP: loopback Host/Origin and a browser client marker — not remote authentication.
  • Fabricated or deserialized actor contexts are rejected.
  • Actor and destination fields in request JSON are never trusted.

touches → web · discord · operations

Delivered

Application operations

One shared set of commands and reads for every entrance, keyed by public UUIDs.

  • Submit persists the message with a stable event ID and returns a receipt. A receipt is admission, not completion.
  • Decide settles one approval; settled decisions are immutable.
  • Read returns bounded pages; observe streams one session over SSE.
  • A disconnected viewer ends its stream, not the work.

touches → ingress · conversations · approvals · Pi Durable

Delivered

Conversations

Sessions, turns, admission and transcript projection.

  • Same event ID and content → same receipt. Different content → conflict.
  • Each channel turn freezes its reply destination.
  • Each session keeps its own provider and model choice.

touches → operations · Pi Durable · models

Delivered

Approvals

The owner approves exact tool arguments before anything runs.

  • Persists the exact arguments and a deadline; expiry wins at that deadline.
  • MCP execution takes a durable claim before calling out.
  • Web can settle a Discord-origin approval; a stale click cannot run it again.
  • Exception: narrowly configured documentation-lookup tools run without a decision.

touches → operations · MCP · Pi Durable

Delivered

Channels & delivery

Bindings map external conversations to sessions. Delivery plans are persisted before any send.

  • States: pending → sending → sent, or uncertain.
  • An unknown send outcome is never blindly retried.
  • Completed tools are never rerun to repair a notification.

02

Follow one turn, through an approval

Delivered behaviour

Choose how the approval ends, then play. A conceptual trace, not live telemetry.

  1. Owner sends a message in Discord or Web.
  2. Ingress verifies identity; the runtime issues an actor context.
  3. The turn is persisted with a stable event ID; a receipt returns. Receipt ≠ completion.
  4. The model proposes a tool call; exact arguments and a deadline are persisted.
  5. Owner approves, rejects, or the deadline passes. Expiry wins at its deadline.
  6. On approval, a durable claim precedes the MCP call; the result is recorded.
  7. A delivery plan is persisted, then chunks are sent and their IDs stored.
  8. An unknown send outcome becomes uncertain — not resent, tool not rerun.

    Switch backends without reloading

    Type a draft, switch, then switch back. The old workspace retires cleanly; the draft waits for its own backend.

    raphie.local / backend A · 127.0.0.1:4316
    workspace A · session 3f2a…
    1. Probe the candidate backend
    2. Abort retired requests, close SSE
    3. Clear query cache, unmount old forms
    4. Save choice, mount a fresh workspace
    Runtime execution on either backend keeps going.

    Migration, backups and failure behaviour

    Startup stores and reads back the OS master before atomically replacing legacy plaintext settings, then cleans the logical file (DELETE journaling, secure delete, VACUUM). Encrypted backups need the matching OS master. Lost master → keys unrecoverable; connection IDs are kept. See credential storage.

    05

    Memory that learns from experience

    First slice + roadmap

    Choose where Raphie remembers. One runtime interface, configurable memory backends, and evidence that survives conversations and compute.

    First slice implemented locally. Settings, built-in memory enabled by default and a connector for Hindsight. Honcho and Obsidian / Markdown remain planned. Built-in memory has lexical search, model-assisted reflection, corrections and logical forgetting; Hindsight has retain, recall and provider reflection, with source management still external. The walkthrough below illustrates the fuller learning lifecycle; built-in consolidation is not implemented. The connector is tested against a local API fixture, not a live Hindsight deployment.

    SETTINGS / MEMORY · FIRST SLICE + ROADMAP

    Choose a memory backend

    Design preview
    Agent turns→Memory interface→Raphie built-in

    Local memory included with Raphie; no external memory service required.

    Configure Enable memory and choose the owner / assistant scope.

    Capability contract SQLite evidence with FTS5 search, source IDs and event time. The agent synthesizes reflections from retrieved evidence. Corrections and logical forgetting are available; consolidation remains planned.

    Illustrative selector only: no connection, credentials, files or memory are changed.

    Connection and switching rules

    Settings saves one active memory configuration with an explicit owner / assistant scope. Named connection libraries are planned. Provider adapters translate stable source IDs and scope into provider-specific banks, workspaces or vault folders. External connections configure endpoint, protected credentials and provider namespace; vault connections configure an allowed path, folders and read/write mode. Save configuration, then test access and inspect capabilities. Built-in memory is enabled by default; no test inserts sample memories. The runtime handles memory; the browser never opens vault files or receives saved secrets.

    Switching changes the selected backend for subsequent work after active memory operations settle. Existing data stays at its original backend. No automatic copying, dual writes, synchronization or outage fallback: imports and migrations require a separate explicit operation. Memory failures and ingestion lag stay visible, and never cause a completed external action to run again. Reuse encrypted Settings secret handling for provider credentials.

    Markdown is a real backend, with a different contract

    An Obsidian vault is a folder of Markdown files, usable without Obsidian running. Treat notes as user-editable source evidence, with file references and external-change reindexing. Raphie can provide retrieval and optional model-assisted reflection over those notes; do not present that as a native vault feature. Keep generated observations distinguishable from authored notes, restrict writes to configured folders, and detect concurrent edits instead of overwriting them. Forgetting, source-note deletion and derived-index removal are distinct operations. Never silently delete a user’s note because a derived memory was forgotten.

    The sequence

    4 done · 5 planned

    Each slice leaves the prototype usable. Select a milestone for its acceptance bar.

    Shared operations and trusted actors

    Web and Discord call the same UUID-keyed submit and decide operations with runtime-issued actor contexts.

    VerifiedWithout a web process, a Discord fixture runs message → approval → exact tool → reply. A stale second click cannot repeat it.

    Channel bindings and frozen destinations

    Discord associations moved into durable bindings; each turn records where its reply goes.

    VerifiedRestarts and duplicate events reuse the same binding, turn and destination. Another thread cannot read its history.

    Durable delivery

    Persisted chunk, card, file and edit plans; each send has a claim and disposition.

    VerifiedSIGKILL after the first chunk: recovery sends only the rest. Unknown chunks stay uncertain.

    Focused queries and observation

    Summary pages, session observations, 50-turn history pages and session SSE replace whole-workspace reads.

    VerifiedAn HTTP client lists, reads, submits and decides without the web app. Local baseline (100 deterministic sessions, 25 viewers): p95 4 ms. Zero sandboxes — not a capacity claim.

    One durable lightweight workspace

    Integrate just-bash with file checkpoints. No host-home or settings mount.

    AcceptanceRestart recovery and isolation between workspaces.

    Experience-based memory

    A configurable Memory interface with built-in, Hindsight, Honcho and Obsidian / Markdown adapters. Settings selects the connection and scope; adapters expose supported operations.

    AcceptanceLearning across sessions and restart, deduplicated ingestion, scope isolation, temporal updates, source-linked reflection, forgetting that invalidates derived knowledge. Verify backend switching, capability reporting and vault edit safety; evaluate relevance and unsupported inferences for each adapter.

    On-demand VM execution

    Capability request, policy, exclusive lease, fenced recovery, explicit transfer, idle cleanup and a budget.

    AcceptanceA real repository test and bulk downloads succeed before choosing the backend. Lost-VM effects stay uncertain.

    Durable follow-through

    Commitments with assignee, deadline, timezone and source. A scheduler owns timing and delivery.

    AcceptanceRestart during the wait; no duplicate notification after recovery.

    Mixed-workload measurement

    Benchmark light tasks and concurrent heavy jobs on the target host.

    AcceptanceStartup and queue latency, success, process-tree memory, CPU, storage and model cost — recorded separately. Limits come from evidence, not identity counts.
