Raphie Architecture

How Raphie is built and why: process topology, the durable execution substrate, the lifecycle of a turn, tool authorization, bot isolation, memory, sandboxes, the extension surfaces, channels and delivery, scheduling, storage, observability and failure behaviour.

Written for engineers who will change it. Statements describe the code as it exists; planned work is labelled planned and never mixed into behaviour. File paths are relative to the repository root.

source: main @ 5d08e5eruntime: Bun 1.4.4 · TypeScript 7generated: 2026-11-05

1System overview

Raphie is a single-owner, self-hosted agent platform. A bot is a persistent assistant identity (personality, sessions, memory, model credentials, tools, schedules, channels, workspace). The owner talks to bots through clients (a web workspace today) and channels (Discord today). All agent work, state and side effects live in one long-running runtime process; everything else is a thin adapter.

1.1 Design constraints

# Constraint Consequence in the code
C1 State that matters must survive any crash point. All mutation is expressed as transactions over durable documents; recovery is a startup transaction, not a special mode (§3.2).
C2 External effects are exactly-once or uncertain, never silently repeated. Tool claims, delivery claims and memory writes are journalled before the effect; an interrupted effect becomes uncertain and is not retried (§6, §12).
C3 One administrator; the host owner is the trust root. No multi-tenant authorization model. Bots are logically separated, not security-isolated (§7).
C4 The core is headless; clients are replaceable. Runtime exposes application operations over HTTP; Discord calls the same operations in-process. The web host owns no domain state (§2).
C5 No operational dependencies beyond the machine. SQLite only, no broker, no cache, no hosted control plane. Two processes, one data directory.
C6 Dependencies point inward; domain code is framework-free. Layered modules enforced by scripts/check-architecture.mjs in CI (§16).

2.2 Boot and shutdown

The runtime is a single Effect.gen program in a scope. Each dependency is an acquireRelease resource, so teardown is the exact reverse of acquisition, on SIGINT/SIGTERM or on failure at any step. The order below is the real acquisition order.

web hostruntimedurable storeexternal systemuncertain / riskplanned
  • Ownership first. ownAppData() writes {pid, token} into runtime-owner.sqlite and refuses to start if the recorded pid is alive (process.kill(pid,0)). No product store is opened before this succeeds, which is what prevents two executors on one journal.
  • Fail closed on keys. If the credential key store is unavailable, BackendSettings.open throws CredentialStoreError and the runtime exits instead of degrading (§13.3).
  • deferResume. The default bot's harness is opened with deferResume: true. Pi tasks are resumed only after BotHost has attached every bot, so every task definition and tool exists before any recovered task runs.
  • Loopback bind, then ready. Bun.serve({hostname:"127.0.0.1", idleTimeout:0, maxRequestBodySize: 4·8 MiB + 64 KiB}). idleTimeout: 0 is deliberate: SSE viewers sit idle while a task waits for an approval.

2.3 Recovery transaction

Crash recovery is a single root.commit executed in Gateway.initialize after the harness opens and before resume. It rewrites in-flight states to truthful ones and backfills older layouts:

Observed at boot Rewritten to Why
Chat / tool / file / plan delivery sending uncertain The send may have reached the platform. Never resend blindly.
Tool approval execution: "running" uncertain + activity action.uncertain The external action may have executed.
Pending non-queued turns left pending; activity run.recovered The harness resumes the chat-reply task from its checkpoint.
Conversations without model / sessionId model from agent state; UUIDv7 sessionId minted Additive migration preserving identities.
Legacy discordThreadId raphie.channel-bindings record + frozen turn.replyTo Reply destinations become immutable per turn.
Deliveries / approvals without connectionId "legacy-discord" Scopes workers per Discord application.

3Request admission and trust boundaries

Authority is issued by trusted adapters, never claimed by a request. There are three independent gates between a browser and a mutation, and one in-process gate for channels.

web hostruntimedurable storeexternal systemuncertain / riskplanned

3.1 Web gateway (apps/web)

createGateway().check(request) runs before the application, the runtime proxy, a server function or an event stream. It returns either a Response (refusal) or an Admission (cookies to set, plus stillValid() for streams). A failure to check is a refusal.

  1. Host allow-list. url.host must match a configured origin; otherwise 403. The single exception is GET /_raphie/health on loopback, which reports ready or locked for the installer's probe.
  2. Public origin from config, never from headers. The listener is HTTP behind a TLS proxy; the public scheme is derived from the configured origin and x-forwarded-* is ignored.
  3. Native device endpoints (/api/auth/device/code|token): POST only; reject any Origin, Cookie, Authorization or Sec-Fetch-Site; require application/json; allow-list body keys (client_id; plus device_code, grant_type for the token call).
  4. Sign-in/out are forwarded to Better Auth with the body bounded to 8 KiB (read incrementally; Content-Length is not trusted) and x-forwarded-for pinned to 127.0.0.1, which yields one shared rate-limit bucket (5 sign-ins/min, 60 other calls/min). One administrator and untrusted forwarding headers make a per-IP limit meaningless; the cost is that anyone who can reach the port can lock sign-in for a minute. raphie auth recover is unaffected.
  5. Session validation per request against auth.sqlite (30-day sessions, daily refresh, HttpOnly, SameSite=Lax, cookie name suffixed by web port). Revocation is immediate.
  6. Unauthenticated: top-level navigations get 303 /login?next=…; API calls get 401, or 503 locked if no administrator exists yet.
  7. Streams: for text/event-stream responses the gateway re-reads the session every streamCheckMs (default 2000 ms) and closes the stream when it ends.

Runtime proxy

apps/web/src/infrastructure/http/runtime-proxy.server.ts serves every /api/*. It re-checks Host and Origin, resolves the runtime base URL (backendAddress), and refuses with 409 backend_changed when the browser's x-raphie-backend / _raphie_backend disagrees with the current backend. It forwards only content-type, x-raphie-client and origin, uses redirect: "error", streams bodies with duplex: "half", propagates the request AbortSignal (so a closed tab closes the upstream SSE) and maps upstream failure to 503.

3.2 Runtime edge (packages/runtime)

Middleware order in bootstrap/http-server.ts:

  1. http.request telemetry span (skipped for /api/diagnostics/* so polling Diagnostics doesn't create a feedback loop).
  2. secureHeaders: CSP default-src 'self', frame-ancestors 'none', base-uri 'none', form-action 'self'; then Cache-Control: no-store.
  3. localAccess: Host must be 127.0.0.1:<port> or localhost:<port>; Origin, if present, must be loopback or a configured web origin; any method other than GET/OPTIONS must carry x-raphie-client: web.
  4. browserCors: exact-origin allow-list, headers content-type, x-raphie-client.
  5. Error mapper: InputError → its status and stable code; HTTPException → its status; anything else → generic 400. Internals never reach the client.
Know the limit. x-raphie-client is a CSRF-style marker, not a credential. The runtime has no authentication of its own: its protection is the loopback bind plus the web gateway in front of it. Anything that can open a socket to 127.0.0.1:4316 with the right Host acts as the owner. Do not expose the runtime port.

3.3 Actors

Operations take an ActorContext {botId, subject:"owner", source, threadId?, connectionId?, discordUserId?}. ActorAuthority.establish() returns a frozen object and records it in a WeakSet; require() rejects any object not in the set. A context therefore cannot be forged, deserialised from JSON or replayed from another bot (each bot has its own ActorAuthority(botId)). HTTP routes mint one owner actor per bot at route composition (runtime.actors.establish("web")); the Discord bridge mints per message, bound to (threadId, applicationId, userId).

3.4 HTTP surface

Per-bot routes are composed by runtimeRoutes(gateway, options); the host mounts the default bot at /api/* and every bot at /api/bots/:botId/* by rewriting the path and delegating to that bot's route table. A route factory receives exactly one bot's runtime and cannot resolve its peers.

4Durable execution model

Raphie does not implement its own job queue or state machine runner. It builds on Pi Durable, a transactional agent harness over a SQL store. Understanding four primitives explains most of the runtime's structure.

web hostruntimedurable storeexternal systemuncertain / riskplanned
Primitive Definition Semantics Raphie relies on
Harness Harness.open(storage, {registry, models, settings}) on bun:sqlite One per bot, one file (gateway.sqlite). Owns conversations, documents, tasks and their recovery. harness.resume() restarts unfinished tasks.
Document defineDoc({kind, version, scope, initial}) Typed JSON state. Read/written only inside a commit(tx) via tx.doc(Doc), observable via harness.snapshot and watchDoc. Many documents may change in one atomic commit.
Task defineTask({name, version, initial, phases, abort}) A resumable state machine. Each phase ends in a commit returning running (with checkpoint), sleeping (until), or terminal. Created inside transactions (tx.createTask), so enqueueing is atomic with the state that motivates it.
Tool defineTool({name, parameters, replay, execute(args, api, ctx)}) Intent is committed before execution. replay: "safe" = the tool's own durable gate makes re-execution harmless; "unsafe" = never re-run after interruption (the outcome is unknown).
Extension defineExtension({name, tools, tasks, sections}) Unit of installation into a registry; may be installed/uninstalled at runtime (§10).

5Lifecycle of a turn

A turn is one admitted message and the agent work that answers it. It has two halves separated by a durable boundary: admission (synchronous, transactional, returns a receipt) and execution (asynchronous, owned by a Pi task).

5.1 Admission algorithm

ChatService.send() runs under connectionGate (mutual exclusion with provider/model configuration changes) and performs everything in one root.commit:

  1. Preconditions. A model must be configured (503 otherwise). messageViolation(): eventId 1–200 chars; text 1–4000 chars (or ≥1 attachment); ≤4 unique attachment IDs, each 64 hex (sha-256); optional positive-integer conversationId.
  2. Idempotency key. requestKey = "<source>:<eventId>"; fingerprint = sha256(JSON[text, conversationId, discordThreadId, attachmentIds?, model?]). If a turn with this key exists: Discord scope and user must match (403), the fingerprint must match (409 otherwise), and the original receipt is returned. This is the retry-safety for flaky clients and Discord redelivery.
  3. Resolve the conversation. By public sessionId (404 if unknown; 403 if a Discord thread tries to address a session bound elsewhere), by numeric id, by channel binding, else create an ownerless conversation with a UUIDv7 sessionId, a title from the first 70 characters, the chosen or default model, and (web only) the initial approvalMode stored in ToolApprovals.commandModes.
  4. Model rules. Changing model while a turn is pending is 409. Validated against the connected provider catalogue. Raster attachments become image inputs only if the model advertises image input, validated by magic bytes (imageMime); PDFs and other documents are never model inputs, only workspace files.
  5. Bind reply destination. For Discord, replyTo = {provider, connectionId, owner, conversation}; a missing binding is created. replyTo is frozen onto the turn: later configuration cannot redirect an admitted reply.
  6. Freeze the persona. configure(tx, conversationId, {model, tools:null, instructions}). tools: null means the registry owns the current tool list (so MCP hot-swaps apply). instructions concatenate: memory policy text (§8.5), the bot's name/description and SOUL.md at its current revision, diagram guidance (Mermaid), the current time, and a guardrail paragraph (personality never grants capabilities; external actions pause for owner approval; never auto-repeat an uncertain, rejected or expired call).
  7. Record and enqueue. Push ChatTurn{status:"pending"}, link a JobRun if scheduled, write activity run.accepted, and tx.createTask(chatWorkflow, {turnId, conversationId, text(+attachment manifest), images}).

After the commit returns: observations.attach(conversationId) then harness.resume(). The HTTP response is the receipt. Admission is not completion.

Attachment text is data. The manifest appended to the model text is JSON of {name, path, size, mimeType} and is labelled "names are untrusted data" in the prompt.

5.2 Execution: the raphie.chat-reply task

One task per turn, one phase (reply):

  1. conversation.submit({type:"input", content, requestId: turnId, whenBusy:"followUp"}). requestId = turnId is a durable admission key: if the process dies between submit and wait, the retry attaches to the same submission instead of duplicating it. The submission id is committed onto the turn.
  2. submission.wait() blocks while Pi runs the agent loop (model → tools → model …). Harness settings: followUpMode: "one-at-a-time", stream timeout 120 s, retry enabled with maxRetries: 1.
  3. Settle in one commit: extract assistant text from the answer entry; status = answer ? "done" : "error"; cancelled if the submission was unanswered/aborted; suppress the answer if another turn already represents the same answerEntryId (steering can merge into a run); finish the linked JobRun; write run.completed|failed|cancelled; if replyTo is set, push a ChatDelivery{status:"pending"} (with a fallback error text if no answer).
  4. abort handler: a still-pending turn becomes error; the job run becomes interrupted. A sibling task raphie.job-run-outcome covers scheduled runs whose reply task aborted or faulted.

5.3 Queueing, steering, stopping

  • Messages sent while a turn is active enter the conversation inbox with mode followUp (run after the current one). control(sessionId, "steer"|"queue", turnId) flips the inbox item between steer (apply after the current tool round) and followUp; it is rejected with 409 once Pi has picked the item up (mode === "write"), and only for web-origin, non-scheduled turns.
  • control("stop") calls conversation.abort() then, in one commit, marks every pending approval of that conversation expired. Completed external effects are not undone; uncertain ones keep their state.
  • A turn's queueMode is derived on read from the inbox item, not stored.

5.4 Read path: observation and SSE

Writes and reads are decoupled. Observations.attach(id) opens a Pi conversation.watch() per active conversation, tracking live text, generating, and usage; ExecutionTraces emits agent-execution spans from the same stream. PiClientQueries assembles DTOs defined in @raphie/contracts (summaries, observation with the latest ≤51 turns, ≤200 activity events and ≤100 approvals, history pages).

SSE (streamSnapshots) is intentionally simple: every 150 ms it computes the authoritative snapshot, JSON.stringifys it, and writes only if it changed; a : heartbeat comment every 15 s while idle; X-Accel-Buffering: no. There is no event-resumption cursor: a reconnect starts from a fresh authoritative state. Viewer disconnect aborts the stream via Hono and never touches durable work.

Cost model. Polling a diff is O(viewers × snapshot cost) and relies on Pi document reads scanning retained state. This is deliberate for now (baseline: 25 idle viewers, p95 4 ms, 83 MiB RSS on the reference machine, no real model calls); indexed reads and push-based invalidation are the obvious next step if scale demands.

6Tool authorization

Every tool that has an effect outside the model is wrapped in the same pattern: ensure → wait → claim → execute → record. The ToolApproval record is the unit of consent and the idempotency ledger for the effect.

Field Meaning
taskId Unique per tool call. ensure() is idempotent per task: a replay returns the existing record.
fingerprint MCP: sha256([connectionIdentity, tool, argumentsJson]). Workspace commands: sha256(["raphie.workspace.command", conversationId, callId, argumentsJson]). If the stored fingerprint differs from the proposal, the call fails ("MCP connection or arguments changed").

6.2 Decision rules (ToolApprovalService.decide)

  • Expiry wins. decideApproval(status, expiresAt, decision, now): non-pending is idempotent; now ≥ expiresAt yields expired regardless of the click.
  • scope: "session" is allowed only for supportsCommandGrant(): server workspace, identity raphie.workspace.command, tool bash|workspace_exec. Otherwise 403. Grants are revocable and survive restart; revoking blocks future claims only.
  • Discord decisions additionally require: same connectionId, same thread as the notification, and the same Discord user who initiated the request. The initiator is recorded only when exactly one turn is pending (otherwise queue ambiguity would assign authority wrongly); in that case only the web UI can decide.
  • Notifications are enqueued as ToolDelivery{kind:"approval"|"resolved"}; the resolved edit replaces the original card. Notification failure never repeats an approved action.

6.3 The claim step

Before any effect, an MCP call re-validates inside a commit: same conversation, same task, same fingerprint, status === "approved", and not fullAccess/grantId (MCP may never ride a command grant, even if a record were forged). Then: execution: "done" → return the cached result; ≠ "waiting" → uncertain ("may have executed; do not repeat"); else set running and write action.claimed. Only then is the remote call made. A thrown error (other than abort) sets uncertain; success sets done with the result stored, so a replay after a crash returns the stored result instead of calling again. 

// packages/runtime/src/domains/approvals/infrastructure/mcp-approval-gate.ts (abridged)
const created  = await approvals.ensure(api, ctx, { server, tool, argumentsJson, fingerprint, connectionIdentity });
const approved = created.status === "pending" ? await approvals.wait(api, ctx, created) : created;
if (approved.status !== "approved") return output({ text: "Tool request " + approved.status + ". No call was sent." , isError: true });
const claim = await api.commit(tx => /* validate + execution: waiting → running */);
// claim.kind: "unauthorized" | "cached" | "uncertain" | "claimed"
result = normalize(await call(approved.id));      // 15 s MCP request timeout
await api.commit(tx => { item.execution = "done"; item.result = result; });

wait() opens a watchDoc(ToolApprovals), resolves on any non-pending status or at expiresAt (timer), and then commits expired if still pending. It is abort-aware (stop interrupts the wait).

7Bots and in-process isolation

BotHost composes one bot runtime per bot inside the single process and owns the registry. A bot runtime is a Gateway (harness + services + workspace) plus its Settings, Memory, MCP, Channels and Jobs.

web hostruntimedurable storeexternal systemuncertain / riskplanned

7.1 Composition

  • Default bot. Built by main.ts and attached first; it keeps the original data paths and session identifiers. It alone receives the shared telemetry sink and RAPHIE_MODEL.
  • Named bots. openIsolatedBot(id, dir) opens BackendSettings, RuntimeMemory (with botId) and Gateway.open({botId, directory: <data>/bots/<id>}) against their own SQLite files. Runtime-issued IDs; created on demand (BotHost.create) and registered once its runtime is open.
  • Automation attach. attach() adds BotMcp (publishing tool sets into gateway.setMcp), BotChannels (Discord), and BotJobs (installing the raphie.jobs task and raphie.scheduling tools).
  • Resume order. After all bots are attached, every harness is resumed. A new bot is resumed after it is registered.
  • Personality. BotProfileStore (bots.sqlite: bot_profiles, append-only bot_revisions; synchronous=FULL) uses optimistic concurrency on revision; the last 50 revisions are retrievable. Edits are refused (409) while the bot has pending turns. Gateway.setPersonality(read) hands ChatService a reader; each turn snapshots it at admission (§5.1).
  • Routing. /api/bots/:botId/* resolves exactly one container; 503 if it is unavailable.

7.2 What is and isn't isolated

Property Holds? Mechanism / caveat
Separate durable state, sessions, approvals, activity Yes One gateway.sqlite and harness per bot.
Separate model credentials, memory, MCP grants, Discord config Yes Per-bot stores; credential AAD binds ciphertext to its record id (§13.3).
Model cannot select another bot Yes Bot identity comes from the container closed over by tool factories, never from tool arguments (createWorkspaceTools, memory tools).
One Discord application ↔ one bot Yes DiscordApplications reserves the application before connecting; duplicates in old data: first bot in profile order wins.
Concurrency Per bot Each bot has its own configuration gate; workspace execution queues per bot, different bots run in parallel.
Process / OS isolation No Same process, user, filesystem permissions, network. A bug in shared code, or the owner, crosses bots.
Per-bot telemetry Not yet openIsolatedBot does not pass a telemetry sink, so named bots emit no operational spans (default bot does).

8.2 Tools and provenance

Tool Input Behaviour
memory_retain content ≤8000, kind Requires an active turn. Evidence id = sha256(sessionId + ":" + callId); source = "session:<id>/turn:<id>"; eventTime = turn.createdAt.
memory_recall query ≤2000 Top ≤8 evidence.
memory_reflect query Built-in returns evidence for the conversation model to synthesize; Hindsight returns provider reflection.
memory_revise · memory_forget id (+content) Built-in only. Removes current evidence, not historical transcripts.

All memory tools are replay: "unsafe": after a crash they are never re-run, so a corrected or forgotten record cannot be resurrected and an external write is never rerouted. Provenance comes from TurnProvenance(conversationId), resolved by the host from the single non-queued pending turn.

8.3 Built-in backend (SQLite + FTS5)

memory_receipts(scope, id)  PK(scope,id)             -- replay guard
memory_evidence(scope,id,content,kind,source,eventTime,revision)  PK(scope,id)
  idx memory_evidence_browse(scope, eventTime DESC, id DESC)
memory_search         USING fts5(scope UNINDEXED, id UNINDEXED, content, tokenize='unicode61')
memory_search_stemmed USING fts5(..., tokenize='porter unicode61')
  • Retain is one transaction: receipt check (a seen id is a no-op, so replay never resurrects a forgotten source or overwrites a correction), evidence insert, both FTS inserts.
  • Recall tokenises to unique Unicode alphanumerics (≤24), builds "t1" OR "t2" …, queries the exact index ordered by rank (limit 8); if fewer than 8, tops up from the Porter-stemmed index, de-duplicated by id. No cached synthesis exists to go stale.
  • Revise bumps revision and re-indexes in both FTS tables in one transaction. Forget deletes from both indexes and the table and rolls back if nothing existed ("never report forgetting something that was not there"). The database runs secure_delete=ON, journal_mode=WAL.
  • Browse is keyset-paged on (eventTime, id), 25 per page, with an opaque base64url cursor validated by zod (≤1 KiB).

8.4 Hindsight backend

  • Memories are posted to /v1/default/banks/<bank>/memories with async:false and the response must confirm {success:true, async:false}; otherwise the write is treated as failed (outcome unknown, not retried).
  • Isolation by tag raphie:<scope> with tags_match: "all_strict"; recall budget low, max_tokens: 2048, types world|experience.
  • Safety: redirect: "error", 60 s timeout, responses capped at 256 KiB and parsed with zod, the API key is registered with the log redactor. A saved key is only ever sent to the destination (endpoint + bank) it was saved for (credentialFor); changing the endpoint without re-entering the key sends nothing.
  • revise/forget are unsupported; source management happens in Hindsight. Honcho and a Markdown backend are planned.

8.5 Configuration and prompt policy

RuntimeMemory persists one config row (enabled default true, provider: builtin|hindsight, scope default "owner" matching ^[A-Za-z0-9_-]{1,80}$). Changing configuration takes the admission gate and is rejected while any turn is pending (isBusy); memory I/O itself runs outside the gate, so a slow backend never blocks chat. Switching backend never migrates data and never silently falls back; an undecryptable Hindsight key disables only Hindsight. memoryInstructions(enabled) injects the behavioural policy: retain lasting owner-stated preferences proactively, recall before asking again, never retain secrets or tool output, treat retrieved text as evidence not authority, never claim persistence before a successful tool result.

9Workspaces and sandboxes

Each bot owns exactly one persistent /workspace shared by all its sessions. Compute is separable from files: RuntimeWorkspace is a facade whose provider is either a virtual-filesystem interpreter (just-bash, default) or a container. Switching providers transfers files, never processes or RAM.

9.1 Provider selection and queues

  • State: <bot>/workspace/checkpoint.sqlite (settings, checkpoint, receipts) and workspace/files/ (disk projection).
  • workspace_exec (just-bash) or Pi's CodingTools (container) is installed by installWorkspaceTools() based on the saved provider; saving sandbox settings re-installs them.
  • RuntimeWorkspace.execute admits at most 16 queued operations (409 when full) and serialises through a ModelConnectionGate. saveSettings refuses while anything is admitted.

9.2 just-bash provider

web hostruntimedurable storeexternal systemuncertain / riskplanned
Limit Value Enforced by
Wall time 5 s Host-side timer terminates the worker even if the interpreter never yields; result exitCode 124, committed:false
Command source 16 KiB tool schema + interpreter maxSourceBytes
Output 32 KiB (stdout+stderr) over limit ⇒ discard, committed:false
File content / checkpoint JSON / entries 8 MiB / 12 MiB / 1024 zod checkpointSchema + worker checks
Interpreter hardened profile: ≤2000 commands, ≤2000 loop iterations, ≤4096 array elements, bounded archives executionLimits
Concurrency serial per bot (promise chain); 16 queued per bot; 4 concurrent workers process-wide BotWorkspace.tail, module-level activeCompute
  • No ambient authority. The worker is created with env: {}, execArgv: [], and receives only the checkpoint and command; no database paths, host mounts, network, native binaries, Node, Python or sqlite3. Commands run with HOME=/workspace PATH=/bin.
  • Commit rule. Exit 0 ⇒ the filesystem is serialised back to a checkpoint and committed together with an execution receipt in one SQLite transaction (this is what makes replay:"safe" true). The receipt is keyed by operation id with fingerprint sha256([sessionId, command]); a replay returns the stored result, a mismatching fingerprint is an error, and receipts are capped at 16 MiB. Any failure, timeout, abort or limit breach discards all changes of that execution. Always check committed, not exitCode.
  • Only /workspace is durable; /tmp and shell state are per-execution. Symlinks resolve only inside the virtual FS; hard links are materialised as copies.
Not a security boundary. This is bounded interpretation of shell syntax in a worker thread. The process account and installed dependencies remain trusted.

9.3 Container provider

web hostruntimedurable storeexternal systemuncertain / riskplanned
Control Value
User --user <host uid>:<host gid>
Capabilities / privileges --cap-drop ALL, --security-opt no-new-privileges, --read-only, --init
Scratch --tmpfs /tmp:rw,nosuid,nodev,size=64m,mode=1777

Budgets 4 containers/process; 4 active ops; 16 admitted per bot; 30 s per command; 16 KiB source; 32 KiB output; 24 MiB RPC; journal 10 000 entries; idle timeout 1–1440 min (reaper)
  • No host-constructed FS. All file operations, readers and watchers run inside the guest: the host bundles Pi's NodeExecutionEnv and drives it with docker exec -i <id> node --input-type=module -e <source> over stdio. A symlink to /etc/passwd resolves to the image's file, not the host's.
  • Lease and epoch fencing. container.sqlite (sibling of, not inside, the mounted files/) holds lease(epoch, scope, workspace_id, container) and a commands journal (id, epoch, method, status, fingerprint, result). Opening a provider increments the epoch and reaps previous-epoch containers (found by raphie.workspace/raphie.scope labels, filtered at the daemon before inspect/stop/rm) — including escaped process groups — before the new epoch is published. A stale provider checks the epoch and can never restart lifecycle work.
  • Command journal. A running row (id, epoch, method, fingerprint) is committed before anything that can mutate files is dispatched. On success the row becomes completed with the stored result (or is deleted when no receipt is retained); a fingerprint mismatch on a known id is rejected. On a transport error the container is removed (to reap orphaned descendants) and the row is marked interrupted, which the tools surface as an unknown outcome.
  • Lazy lifecycle. One container per bot, created on first use (sleep infinity), removed after idleMinutes; files persist, processes do not. If the daemon is down at boot the bot starts with the container provider marked unavailable; files are preserved and other bots are unaffected.
  • Tools. read/write/edit/bash from @earendil-works/pi-durable/tools. bash goes through the command approval gate (§6) and is replay:"safe"; the others are replay:"unsafe" so interrupted native effects are never rerun. Commands have no rollback.

9.4 Provider switching

saveSettings runs under the workspace gate: validate; refuse if any operation is admitted; acquire a newer container epoch first (even when switching away) so every native writer is fenced before either representation is read; migrate files between checkpoint.sqlite and files/ (diskCheckpoint, publishCheckpoint, migrateCheckpoint, crash-recoverable via recoverDisk); persist settings; on failure, re-open the previous epoch. The HTTP layer additionally refuses (409) while the bot has pending turns.

9.5 Attachments and documents

Uploads are content-addressed (sha-256 hex id; ≤8 MiB each; ≤4 per message) in local-attachment-store.ts and copied into the workspace by putFile under the same queue and provider rules; originals remain downloadable if the working copy changes. createDocumentTools adds document extraction tools backed by @firecrawl/anydoc-wasm and pdfjs-dist running in a worker, so PDFs and office files are read by tools, not fed to the model as documents.

"Plugin" means three distinct things in Raphie. They share a philosophy — explicit, narrow contracts; plugins never grant authority — but live at different layers.

10.1 Runtime extensions (Pi registry)

10.2 MCP (external tools)

  • Transports. Streamable HTTP (URL + optional bearer) or stdio (command, argv JSON, explicit env). Legacy SSE is unsupported. Pi's MCP client owns initialisation, paginated discovery, cancellation and shutdown; request timeout 15 s.
  • Hardening. HTTP(S) URL with no embedded credentials; bearer tokens require HTTPS (loopback exempt); redirect: "error"; stdio children get inheritEnv:false, only PATH plus supplied env; calls to tools the server did not advertise are rejected locally. stdio servers run as the runtime user and are not sandboxed.
  • OAuth. For servers supporting discovery + dynamic client registration, McpOAuth runs a one-grant, one-callback loopback server (PKCE and state validated by Pi's provider; returned issuer checked), consent expires after 5 minutes, authorizationGeneration invalidates prior account grants, tokens are encrypted per bot connection. The browser must be on the runtime machine to reach the loopback callback.
  • Naming and size. mcp_<namespace>_<tool>, non-[A-Za-z0-9_] replaced; names over 64 chars are truncated plus an 8-hex sha-256 suffix; duplicates fail registration. Results are text-normalised and truncated at 30 000 chars; non-text parts become placeholders.
  • Policy. Every call goes through the §6 gate. Discovery never implies approval.

Plugins are compiled into the web bundle and registered in a static array (today: raphie.token-counter). 11Channels and delivery

A channel is an external messaging platform; a client is an application. Both reach the same application operations (SessionOperations: submit, submitScheduled, decide, control, chooseModel, grants/mode, file-copy), differing only in how identity is established and how output is delivered. Channel adapters receive an explicit ChannelServices port {telemetry, actors, sessions, files, deliveries} and never import the process host.

11.1 Bindings and reply destinations

A ReplyDestination is {provider:"discord", connectionId, owner:"owner", conversation}. A ChannelBinding adds sessionId and associates an external conversation with exactly one session; it does not share that session with other conversations. Web-origin turns have replyTo: null. There is no session-linking operation: a Discord thread keeps its own session.

11.2 Discord bridge

  • Ingress is Gateway events only (WebSocket via the Chat SDK). HTTP webhooks are rejected: webhookVerifier: () => false unless a public key is configured.
  • Authorization (discordAuthorized) applies identically to messages and button interactions: the user id must be in the allow-list and, when a target is configured, guild, channel and (if set) thread must match. Bots' own messages are ignored. Message text can never name a session id.
  • Handlers: new message, mention, DM, subscribed-thread message → sessions.submit(actors.establish("discord", threadId, applicationId, userId), {eventId: message.id, text}). The message id is the idempotency key (§5.1). Buttons raphie-tool-approve|reject call sessions.decide (§6.2).
  • Chat is text-only on Discord today. The legacy /copy command downloads ≤4 attachments (≤8 MiB each) from cdn.discordapp.com|media.discordapp.net only (https, no port/userinfo, redirect:"error", 15 s) into the file-approval experiment.
  • Credentials. The application id is resolved from the bot token (/oauth2/applications/@me), and channel/guild consistency is verified against the REST API at configuration time. Tokens are encrypted with the bot's credential cipher. SDK logging is silenced because info logs include message content.

11.3 Durable delivery

Outbound messages are intents recorded in the originating document (ChatDelivery, ToolDelivery, file deliveries). A worker per Discord application turns an intent into a persisted plan before any I/O.

  • Discord renders long replies into chunks of 1900 characters. claim(render) is a transaction: pick the next pending operation of an in-scope plan, or else the next pending intent (tool, then file, then chat), render it locally into N payloads (chunks, cards, files, edits), insert a DeliveryPlan with operation 0 sending, and mark the intent sending. Rendering happens before any claim or network call.
  • settle(id, messageId|null) requires the operation to be sending; messageId ⇒ sent, null (any thrown error) ⇒ uncertain. When no operation remains pending/sending, the intent becomes sent only if all operations were sent; otherwise uncertain with "inspect the platform before retrying".
  • An uncertain chunk is not repeated, but later pending chunks still send. A resolved-approval notification edits the original card (originalMessageId) instead of posting.
  • The worker is single-flight (running flag), scoped to one connection via forConnection(applicationId), and emits a delivery.send span.

12Scheduled work

Schedules are Pi tasks, not timers. BotJobs creates one raphie.recurring-prompt task per enabled job; Pi owns sleeping, checkpoints and recovery.

web hostruntimedurable storeexternal systemuncertain / riskplanned
  • Creation is transactional. schedule(tx, input) inserts the job and its task in one commit; agents manage jobs via schedule_* tools whose receipts (raphie.schedule-mutation) commit in the same transaction. Limit: 100 jobs per bot.
  • Idempotence. Run id and admission eventId are job:<taskId>:<scheduledAt>, so a crash between phases cannot double-admit.
  • Never overlap interactive work. If the bot is busy (pending turn or approval) the task sleeps 5 s and retries; "Run now" is refused while busy.
  • Replacement, not mutation. Updating a job creates a new task and retires the old one; a task whose id no longer matches job.taskId terminates itself (replaced).
  • Scheduled turns use submitScheduled; the stored prompt is wrapped by scheduledInstruction() so the model writes the reminder rather than answering as if asked. Run history (raphie.job-runs) retains active and unread runs plus the newest 500 acknowledged; unread completions surface as notifications.
  • Failure semantics. A failed submission records lastStatus:"failed" without persisting transport error payloads; one-shot jobs disable themselves after their first attempt.

13.2 Evolution

Document kinds stay at version: 1 with additive fields and an explicit backfill in the recovery transaction (§2.3). Public identifiers are UUIDv7 session ids; numeric conversation ids remain internal and legacy links resolve through /api/sessions/legacy/:id. An older executable is not a supported reader of a newer layout; downgrade means restore a pre-upgrade backup or roll forward. Back up with SQLite's backup API or with the runtime stopped; copying a live file can miss WAL content.

13.3 Secrets

  • Cipher. AES-256-GCM, 12-byte random nonce, 16-byte tag. AAD is the JSON ["raphie-provider-key-v4", keyId, recordId, provider], binding ciphertext to its record and provider so rows cannot be swapped.
  • Master key. 32 random bytes keyed by a random keyId, stored outside app data: OS credential store via Bun.secrets (service com.raphie.provider-credentials), or, when RAPHIE_CREDENTIAL_KEY_FILE is set, an owner-only file. A new key is read back before any plaintext is replaced. SQLite holds ciphertext and the non-secret keyId only.
  • Fail closed. A missing/locked store throws CredentialStoreError (503) with no automatic fallback; store errors are never propagated because they can embed secret material. Keys never appear in read responses.
  • Redaction. Activity details and logs pass through redact(); secrets are registered with registerRedactionSecret when decrypted.

15Web application

apps/web mirrors the runtime's domain layout (domains/<ctx>/{application,infrastructure,presentation}) plus presentation/workspace (shell), infrastructure/{auth,http,preferences} and shared/{ui,styles,syntax}. Routes (bootstrap/routes): /, /sessions/$sessionId, /login, /device, and /api/$ (the proxy). UI primitives come from Base UI (the architecture check rejects Radix imports).

  • Contracts, not internals. The browser imports only @raphie/contracts — framework-free DTOs and pure projections (run-projection, reply ledger). No web module may import the runtime package (enforced).
  • Focused reads. It composes summary pages and a selected-session observation (SSE) and loads older history/diagnostics on demand; it does not subscribe to the whole workspace.
  • Composer. Queued/steering/stop controls map 1:1 onto §5.3; the command-permission selector sets approvalMode at conversation creation; drafts and attachment drafts are browser-only (localStorage, uploads held by id).
  • Backend connection. The workspace tracks which backend it was opened against and refuses stale requests with backend_changed (§3.1).

16Code organisation, build and release

16.1 Layering (enforced)

scripts/check-architecture.mjs statically scans imports and fails the build on:

  • domain/ or application/ importing infrastructure|presentation|bootstrap; domain/ importing application/; core layers importing any non-relative package other than @raphie/contracts.
  • Anything outside bootstrap importing bootstrap/; shared/ importing domains/bootstrap/presentation.
  • apps/web importing the runtime; web importing Radix; non-entrypoint files in a source root.

It is a static import check, not proof of absence of semantic coupling.

16.2 Packaging and distribution

  • Standalone build (scripts/build-standalone.sh <bun-target> <version> <build-id>) produces raphie, raphie-runtime, raphie-web and a diagnostic raphie-smoke via bun build --compile. The just-bash worker is compiled in as a second entrypoint (workspace-worker.ts) and resolved by path in the binary (Bun.isStandaloneExecutable); the container guest and document worker are bundled separately and embedded as assets, alongside the anydoc WASM. dotenv/bunfig autoload is disabled.
  • Targets: glibc Linux x64/arm64 and macOS x64/arm64 for the user installer; Windows is deferred. The launcher starts the two executables from its own directory.
  • Installers: scripts/install.sh (user, no sudo; ~/.local/lib/raphie, ~/.local/bin/raphie, PATH block, user service via systemd or launchd) and a system-wide Linux installer with systemd unit, backups and restore. Archives are verified against SHA256SUMS (integrity, not provenance).
  • Channels: stable (default; install stops if none) and nightly (built from main after validation, version vX.Y.Z-nightly.<date>.<run>.<attempt>); the choice is remembered for updates. macOS binaries are unsigned.
  • CI (.github/workflows): ci.yml runs bun run validate (format, architecture, oxlint type-aware, TypeScript, tests, build) after building the container test image; release.yml prepares tagged and nightly releases; standalone.yml covers the standalone build. Tests use temporary SQLite databases and deterministic models — no paid inference, no live Discord.
