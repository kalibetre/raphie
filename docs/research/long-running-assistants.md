# Long-running assistants

Research snapshot, 26 November 2026. GitHub star counts are rounded as displayed. Release links indicate recent published activity or the latest release observed. Behavior is based on primary documentation and the linked source paths. No projects were installed or benchmarked.

## Summary

- **OpenClaw is the closest product comparison.** One default direct-message session can keep going indefinitely, isolated jobs and subagents can return results to the originating chat, and jobs have inspectable run history. Its current heartbeat migration turns periodic checks into ordinary editable jobs. [Sessions](https://docs.openclaw.ai/concepts/session#session-lifecycle), [automation execution styles](https://docs.openclaw.ai/automation/cron-jobs/payloads), [heartbeat migration](https://github.com/openclaw/openclaw/blob/v2026.11.10/docs/gateway/heartbeat.md), [subagent delivery](https://docs.openclaw.ai/tools/subagents/announce).
- **Letta provides the strongest memory-maintenance comparison.** Recall can recover evicted messages, a small memory tier can stay in the prompt, and a background agent can consolidate durable learning independently of replies. Letta's product also supports multiple conversations for each agent. [Context affordances](https://github.com/letta-ai/context-constitution/blob/main/constitution/AFFORDANCES.md), [memory and dreaming](https://docs.letta.com/configuration/memory), [stateful agents](https://docs.letta.com/concepts/stateful-agents).
- **Raphie's current summary policy is a reasonable baseline.** It starts around 64k on large windows, retains up to 20k recent tokens, scales down on smaller models, and recovers from overflow. The next investments should be authoritative work items and recovery of exact transcript details. Evaluate token savings and recall before changing the thresholds. [Raphie execution](../../apps/docs/src/content/docs/architecture/execution.mdx#summarizing-long-sessions), [Raphie domain model](../../CONTEXT.md), [Lossless Claw architecture](https://github.com/Martian-Engineering/lossless-claw/blob/main/docs/architecture.md), [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence).

The six projects cover two assistant products, a stateful agent platform, a workflow framework, and two memory components. Work-item recommendations are design inferences. In Raphie, the chat is the owner's ongoing exchange, a session is model context, and a work item is the durable record of something the bot is keeping track of. Those distinctions matter when comparing projects that call all three a thread. [Raphie domain model](../../CONTEXT.md).

## OpenClaw

**Product and maturity.** Self-hosted, multichannel personal assistant, originally Clawd/Clawdbot and then Moltbot. GitHub displayed about **395k stars**, MIT, with the `v2026.11.10` release published on 25 November. The local Gateway owns channel connections, routing, tools, sessions and automation. The Control UI and CLI connect to it. Current docs put session rows and transcripts in a per-agent SQLite database and describe JSONL and `sessions.json` as migration sources. Job definitions and run history live in shared SQLite state. [Author's rename post](https://openclaw.ai/blog/introducing-openclaw), [repository](https://github.com/openclaw/openclaw), [release](https://github.com/openclaw/openclaw/releases/tag/v2026.11.10), [session storage](https://docs.openclaw.ai/concepts/session), [automation lifecycle](https://docs.openclaw.ai/automation/cron-jobs/how-it-works).

**Chat model.** Direct messages default to the same per-agent main session across channels. Peer/channel/account isolation is configurable, and group/topic routing has separate session keys. Current docs default to no timer-based reset, with daily, idle and explicit resets available. Dashboard/session maintenance can archive or prune old sessions, so a stable active session key comes with a storage retention policy. [Session management](https://docs.openclaw.ai/concepts/session), [channel routing](https://docs.openclaw.ai/channels/channel-routing).

**Context and cost.** Built-in managed-loop maintenance checks projected occupancy against the smaller of 85% of the active window and the window minus the reserve, subject to a server-specific floor. Provider overflow can trigger compaction and retry, and optional maintenance can run after reply delivery. Manual compaction keeps a configurable recent tail with a documented 20k-token default. That is a separate setting from the reserve. Safeguard compaction carries decisions, open work and exact identifiers forward, reconciles newer corrections with the prior summary, and moves the cut to preserve tool call/result pairing. Very long summarizer input can be sampled. Eligible routes can summarize using the warm prompt prefix, and provider-specific cache-TTL pruning removes older tool-result content from the model projection while retaining the transcript. [Compaction reference](https://docs.openclaw.ai/reference/session-management-compaction/compaction), [warm-request compaction](https://docs.openclaw.ai/concepts/compaction#warm-request-compaction), [session pruning](https://docs.openclaw.ai/concepts/session-pruning).

**Concurrent work and delivery.** Persistent automations cover one-shot, recurring and condition-triggered runs. The job picks an execution context and a delivery destination independently. A current-session job runs in a child context with a bounded excerpt of the originating chat. An isolated job starts fresh, and an announce result can still return to the origin or a configured destination. An agent can manage jobs conversationally, with separate UI/CLI inspection of runs. Older heartbeat configuration and `HEARTBEAT.md` migrate to editable jobs with scratch state and history. The current automation docs say the shared Tasks ledger and TaskFlow API were removed. Native subagents still have their own lifecycle registry and return completions to the requester with duplicate suppression. A retained child session alone does not make its completed run ongoing. [Schedules](https://docs.openclaw.ai/automation/cron-jobs/schedules), [execution styles](https://docs.openclaw.ai/automation/cron-jobs/payloads), [job management](https://docs.openclaw.ai/automation/cron-jobs/managing-jobs), [delivery](https://docs.openclaw.ai/automation/cron-jobs/delivery), [heartbeat migration](https://github.com/openclaw/openclaw/blob/v2026.11.10/docs/gateway/heartbeat.md), [tagged automation migration](https://github.com/openclaw/openclaw/blob/v2026.11.10/docs/automation/index.md#L61-L69), [subagent completion](https://docs.openclaw.ai/tools/subagents/announce), [subagent lifecycle](https://docs.openclaw.ai/concepts/subagent-yield-handoff).

**Memory.** Workspace Markdown separates stable user information, curated durable facts and dated observations. The model can write notes during regular work and gets a memory checkpoint before compaction where configured. A background dreaming sweep can promote grounded observations. The built-in index offers keyword search and can combine it with vector search when embeddings are configured. The docs advise replacing a changed preference in the current profile while preserving useful dated history. [Memory overview](https://docs.openclaw.ai/concepts/memory), [compaction and memory flush](https://docs.openclaw.ai/concepts/compaction), [dreaming](https://docs.openclaw.ai/concepts/dreaming).

**Raphie takeaway.** Use the job/result routing pattern and duplicate suppression. Persist the work item's lifecycle through successive executions and keep its identity independent of both the chat and individual runs. For recall, the optional Lossless Claw plugin shows a more ambitious design. SQLite stores source messages, a summary DAG links summaries back to those messages, and search/expand tools recover details. Raphie can test source links and transcript search with its existing transcript before adding a second store or a DAG. [Automation delivery](https://docs.openclaw.ai/automation/cron-jobs/delivery), [subagent delivery](https://docs.openclaw.ai/tools/subagents/announce), [Lossless Claw architecture](https://github.com/Martian-Engineering/lossless-claw/blob/main/docs/architecture.md), [Raphie domain model](../../CONTEXT.md).

## Letta

**Product and maturity.** Stateful agent platform originating in MemGPT. The server repository displayed about **25.6k stars**, Apache-2.0, and release `0.16.8`. Distinguish the Python REST server, which documents Docker and PostgreSQL with pgvector, from the newer Letta Code/App Server, whose WebSocket API exposes agent, subagent, memory and schedule operations. The v1 server distinguishes server-side sandboxed tools from externally executed MCP and client tools. Letta's app documents channels such as Slack, alongside web and CLI use. [Repository](https://github.com/letta-ai/letta), [server releases](https://github.com/letta-ai/letta/releases), [MemGPT paper](https://arxiv.org/abs/2310.08560), [Docker server](https://docs.letta.com/v1-sdk/docker), [App Server protocol](https://docs.letta.com/self-hosting/app-server/protocol-lifecycle), [v1 agent components](https://docs.letta.com/v1-sdk/concepts/stateful-agents), [Letta app](https://www.letta.com/agent/).

**Chat and concurrent work.** An agent has a default conversation and can also have multiple independent conversations sharing identity and memory. In the app/CLI, Letta recommends separate conversations for parallel threads. Subagents can use isolated history and hand a result back to the parent. The v1 API documents one-off and cron-scheduled messages with an optional callback, and the App Server exposes schedule and run history. These sources establish ways to run concurrent and scheduled work. They do not establish a single owner chat that always receives every result, or an always-present list of open commitments. The MemGPT paper's heartbeat requests continued model execution through a tool call. This mechanism differs from an interval scheduler. [Default conversation API](https://docs.letta.com/api/python/resources/conversations/subresources/messages/methods/compact), [product conversation model](https://docs.letta.com/concepts/stateful-agents), [subagent workflows](https://docs.letta.com/configuration/workflows), [server schedule API](https://docs.letta.com/api/resources/agents), [App Server protocol](https://docs.letta.com/self-hosting/app-server/protocol-lifecycle), [MemGPT paper](https://arxiv.org/abs/2310.08560).

**Context and cost.** The tagged `0.16.8` threshold helper returns **90% of the configured window** unconditionally, despite a docstring describing two model-specific thresholds. The constant is `0.9` and the fallback configured window is `128000`. This is the tagged server helper, with no claim about every harness or hosted route. Default agent-mode `sliding_window` selects a token-checked cut, preserves recent messages and a pending approval, and inserts the new summary ahead of the retained messages. The target in code is `(1 - sliding_window_percentage) × context_window` even though the schema describes the field as the retained fraction. At the default `0.30` the target before adding the new summary is about 70%. All-message and self-compaction variants exist. The summary prompts preserve plans and references such as files and PRs. Old messages remain accessible through history/search. Separate compaction can use a lighter model. Self-compaction can reuse the agent's context prefix, and the authors recommend positioning frequently edited memory after stable content to reduce cache invalidation. [Tagged threshold](https://github.com/letta-ai/letta/blob/0.16.8/letta/services/summarizer/thresholds.py#L24-L37), [tagged constants](https://github.com/letta-ai/letta/blob/0.16.8/letta/constants.py#L69-L75), [tagged configuration](https://github.com/letta-ai/letta/blob/0.16.8/letta/services/summarizer/summarizer_config.py#L43-L75), [tagged settings default](https://github.com/letta-ai/letta/blob/0.16.8/letta/settings.py#L66-L77), [tagged window selection](https://github.com/letta-ai/letta/blob/0.16.8/letta/services/summarizer/summarizer_sliding_window.py#L115-L180), [release notes](https://github.com/letta-ai/letta/releases/tag/0.16.7), [author-maintained compaction guide](https://github.com/letta-ai/skills/blob/main/letta/self-configuration/SKILL.md), [Context Constitution](https://www.letta.com/constitution/).

**Memory and sleep-time compute.** In the server design, editable pinned blocks hold core context, indexed messages provide recall, and a separate vector archive holds deliberately saved knowledge. The original sleep-time implementation pairs the foreground agent with an independently configured agent that updates shared pinned blocks in the background, taking memory-write tools off the primary agent. The newer product moves memory to Git-backed MemFS and replaces server sleep-time agents with client-side subagents. MemFS exposes an index of available files, loads `system/` content into the prompt, and lets the agent read the rest on demand. Reflection can review recent history in a worktree and merge a versioned memory update. The CLI/app documents step-count and compaction triggers, with optional model review of proposed changes. Defragmentation consolidates duplicates and reorganizes files. That maintenance has its own token cost. [V1 agent memory](https://docs.letta.com/v1-sdk/concepts/stateful-agents), [archival memory](https://docs.letta.com/v1-sdk/memory/archival-memory), [original sleep-time design](https://www.letta.com/blog/sleep-time-compute/), [server feature transition](https://www.letta.com/blog/our-next-phase/), [MemFS design](https://www.letta.com/blog/context-repositories/), [dreaming controls](https://docs.letta.com/configuration/memory).

**Raphie takeaway.** Trial an after-reply memory review over a bounded interval of completed owner turns. Let it propose source-linked amendments and supersessions in the existing memory backend. Capture the reviewed transcript boundary and check the latest revision before applying a write. Keep owner instructions and live work status authoritative in their existing domains. The model can retrieve seldom-used evidence by pointer without pinning all of it. [Letta context repositories](https://www.letta.com/blog/context-repositories/), [Context Constitution](https://www.letta.com/constitution/), [Raphie domain model](../../CONTEXT.md).

## Khoj

**Product and maturity.** Self-hostable personal research assistant with custom agents and scheduled research. GitHub displayed about **38.3k stars**, AGPL-3.0, and its latest release page resolved to **2.0.0-beta.28**. Implementation findings below refer to the inspected `master` source. The Python chat routes use Django model adapters, the Compose stack includes PostgreSQL/pgvector, and automation uses APScheduler cron triggers and Django job records. The project ships web and client integrations. [Repository](https://github.com/khoj-ai/khoj), [release](https://github.com/khoj-ai/khoj/releases/tag/2.0.0-beta.28), [self-host setup](https://docs.khoj.dev/get-started/setup/), [Compose](https://github.com/khoj-ai/khoj/blob/master/docker-compose.yml), [job scheduler](https://github.com/khoj-ai/khoj/blob/master/src/khoj/routers/helpers.py#L2426-L2479), [adapters](https://github.com/khoj-ai/khoj/blob/master/src/khoj/database/adapters/__init__.py).

**Chat and context.** The chat API lists and creates sessions, including a selected agent, so the product supports multiple chats. The inspected prompt builder computes a lookback from `max_prompt_size // 750`, limits assembled history entries as a multiple of that lookback, then counts tokens and removes old history or trims oversized context. Missing model-specific prompt size falls back to 10k in this path. The latest assembled chat messages survive subject to that budget. User memory is injected separately with dates. I found no rolling conversation summary or prompt-cache policy in this prompt assembly path. [Session routes](https://github.com/khoj-ai/khoj/blob/master/src/khoj/routers/api_chat.py#L470-L540), [prompt assembly and truncation](https://github.com/khoj-ai/khoj/blob/master/src/khoj/processor/conversation/utils.py#L621-L861).

**Concurrent work and delivery.** A chat request can create a recurring query. The scheduler obtains a query, subject and cron time, persists an automation, and calls the chat endpoint when it fires. With a stored conversation ID it reuses that chat, and the runner removes the automation if the chat has disappeared. Khoj has an automation management surface, and it uses a model decision to suppress unnecessary email. The self-hosted email integration requires Resend and authentication. This delivers scheduled research and monitoring without establishing a general work-item lifecycle for unscheduled follow-ups. [Automation guide](https://docs.khoj.dev/features/automations/), [scheduled query and notification](https://github.com/khoj-ai/khoj/blob/master/src/khoj/routers/helpers.py#L2292-L2479).

**Memory.** With memory enabled, each chat request combines recent rows (up to ten updated in the last seven days by default) and query-similar rows ranked by cosine distance, deduplicated by ID. The default agent takes the user-wide query branch, while a custom agent adds an agent filter. After logging a regular turn, the code awaits a fast-model extraction over the new messages and the retrieved memories. The result lists facts to create and memory IDs to delete. Automation turns skip this write path. This gives a concrete way to correct retrieved memories, with coverage limited by which prior memories were supplied as candidates. [Retrieval path](https://github.com/khoj-ai/khoj/blob/master/src/khoj/routers/api_chat.py#L909-L916), [memory queries](https://github.com/khoj-ai/khoj/blob/master/src/khoj/database/adapters/__init__.py#L2089-L2158), [extractor](https://github.com/khoj-ai/khoj/blob/master/src/khoj/routers/helpers.py#L916-L987), [memory write gate](https://github.com/khoj-ai/khoj/blob/master/src/khoj/processor/conversation/utils.py#L557-L575).

**Raphie takeaway.** Adopt a source-aware write policy. Form owner preferences from owner-authored evidence and let recurring runs update their own work item or propose separately attributed observations. Retain independent job and chat lifecycles so a chat rewind can leave actual scheduling effects visible. For monitoring results, check a durable state change before spending tokens on notification copy. [Khoj automation execution](https://github.com/khoj-ai/khoj/blob/master/src/khoj/routers/helpers.py#L2322-L2424), [Khoj write gate](https://github.com/khoj-ai/khoj/blob/master/src/khoj/processor/conversation/utils.py#L557-L575), [Raphie rewind and scheduled work](../../CONTEXT.md).

## LangGraph and its companion packages

**Framework and maturity.** LangGraph is a graph execution framework with durable checkpoints, streaming and interrupts. GitHub displayed about **45.5k stars**, MIT, with core release **1.2.24** in the observed release list. A checkpointer scopes execution state to `thread_id`, and a Store provides cross-thread data. The open-source library exposes storage adapters, including SQLite and PostgreSQL checkpointers. The separate LangSmith Agent Server product adds an API and a background worker pool with PostgreSQL and Redis. Deep Agents and LangMem are companion packages. Their defaults and APIs apply when those components are selected. [Repository](https://github.com/langchain-ai/langgraph), [releases](https://github.com/langchain-ai/langgraph/releases), [persistence](https://docs.langchain.com/oss/python/langgraph/persistence), [Agent Server data plane](https://docs.langchain.com/langsmith/data-plane), [LangMem](https://github.com/langchain-ai/langmem), [Deep Agents](https://docs.langchain.com/oss/javascript/deepagents/overview).

**Chat and context.** An application can keep using one checkpoint thread or allocate several. Presentation and routing belong to the application. Bare LangGraph supplies no universal summarization threshold. Its memory guide shows building a rolling summary node and choosing the trigger, summary budget and messages to keep. The Python Deep Agents harness provides a concrete preset. At 85% of the model's advertised input window it summarizes intent, artifacts and next steps, retaining 10% of the input budget as recent context. Without a profile the preset uses a 170k trigger and six retained messages. It handles recognized overflow by summarizing and retrying, supports an alternate summarizer, preserves the persisted history, and can offload large tool results to a file reference with a preview. Provider prompt caching is an integration choice. [LangGraph memory guide](https://docs.langchain.com/oss/python/langgraph/add-memory), [Deep Agents context engineering](https://docs.langchain.com/oss/python/deepagents/context-engineering), [LangChain provider middleware](https://docs.langchain.com/oss/python/langchain/middleware/built-in).

**Concurrent work and delivery.** Graph state and checkpoints make execution resumable, including at an approval interrupt. Deep Agents has `write_todos` for plan progress and a subagent tool that returns a final report into the parent context. LangSmith Agent Server provides background run IDs and join/status calls, a same-thread enqueue strategy, and crons targeting either an existing thread or a fresh thread per tick. The app still needs to own the relation among an open work item, its runs and the owner-visible message. [Graph state and interrupts](https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph), [Deep Agents capabilities](https://docs.langchain.com/oss/javascript/deepagents/overview), [background runs](https://docs.langchain.com/langsmith/background-run), [enqueue strategy](https://docs.langchain.com/langsmith/enqueue-concurrent), [cron jobs](https://docs.langchain.com/langsmith/cron-jobs).

**Memory.** Stores expose namespaced JSON documents, optionally with semantic indexing. The guide describes a stable profile record versus a collection of individually retrievable facts. Application code decides what to retrieve or write on the request path, when to run background extraction, and how to replace stale data. LangMem offers extraction and consolidation utilities and tools for managing memory. Deep Agents can route only a designated memory path through a Store while leaving other files scoped to the checkpoint thread. [LangGraph memory](https://docs.langchain.com/oss/python/langgraph/add-memory), [memory write models](https://docs.langchain.com/oss/python/concepts/memory), [LangMem](https://github.com/langchain-ai/langmem), [Deep Agents backends and memory](https://docs.langchain.com/oss/python/deepagents/context-engineering#long-term-memory).

**Raphie takeaway.** Keep chat display, work-item state and model input as separate projections of durable state. Give each open work item that actually needs execution one resumable background session. Deliver a small result into the chat using the originating message's quote and preserve the full result as a linked artifact. Deep Agents' tool-output offloading is worth testing before summarizing increasingly large tool transcripts. These patterns fit Pi Durable's existing runtime. [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence), [Deep Agents offloading](https://docs.langchain.com/oss/python/deepagents/context-engineering#offloading), [Raphie execution](../../apps/docs/src/content/docs/architecture/execution.mdx), [Raphie domain model](../../CONTEXT.md).

## Graphiti and Zep

**Component and maturity.** Graphiti is Zep's open-source Python temporal graph library. Its repository displayed about **33.1k stars**, Apache-2.0, and the core **0.32.1** release on 24 November. Graphiti wires a graph driver to LLM extraction, embeddings and search/reranking. Documented drivers include Neo4j, FalkorDB, Neptune and embedded Relate. The repo ships reference REST and MCP interfaces. Zep's hosted API adds users, message threads, ingestion and context assembly. The hosted API behavior below comes from its v4 docs. [Repository and architecture](https://github.com/getzep/graphiti), [release](https://github.com/getzep/graphiti/releases/tag/v0.32.1), [Zep threads](https://help.getzep.com/threads), [Zep paper](https://arxiv.org/abs/2501.13956).

**Chat, context and work.** Graphiti receives episodes from the caller. In hosted Zep, one user can have many message threads whose histories feed the same user graph. The host application still owns chat compaction, the verbatim tail, caching and task presentation. The documented `thread.get_context()` uses the four most recent thread messages to query the user graph and returns a configurable block that can include a user summary, facts, entities, episodes, observations and thread summaries. Zep recommends supplying four to six recent messages directly to the model while ingestion catches up. Ingestion tasks track processing of submitted data. I found no owner-facing work-item, reminder or background agent runtime in the inspected Graphiti interfaces. [Episode API](https://help.getzep.com/graphiti/core-concepts/adding-episodes), [thread ingestion](https://help.getzep.com/threads), [context assembly and freshness](https://help.getzep.com/retrieving-context), [ingestion tasks](https://help.getzep.com/v4/adding-business-data), [reference servers](https://github.com/getzep/graphiti).

**Memory.** `add_episode` accepts timestamped message, text or JSON input. Ingestion extracts entities and relationships, resolves existing nodes and edges, and links facts to source episodes. Similar facts can share an edge. For a contradiction, the implementation uses the inferred validity interval to close a superseded fact and retains the history. `valid_at` and `invalid_at` describe when a fact held. `created_at` and `expired_at` record when the system learned or invalidated it. Graph retrieval combines semantic and keyword matches, with graph-distance reranking available. The paper reports memory benchmark improvements under its chosen setup. Raphie would need its own evaluation of commitments, provenance and external effects. [Graphiti ingestion source](https://github.com/getzep/graphiti/blob/main/graphiti_core/graphiti.py#L1510-L1589), [temporal invalidation source](https://github.com/getzep/graphiti/blob/main/graphiti_core/utils/maintenance/edge_operations.py#L698-L759), [Graphiti search](https://help.getzep.com/v2/graphiti/getting-started/quick-start), [Zep facts and time](https://help.getzep.com/v4/facts), [Zep paper](https://arxiv.org/abs/2501.13956).

**Raphie takeaway.** Borrow validity and provenance first. A SQLite memory record can link to the source message, track when something was observed, and record an explicit supersession for a changed preference. That supports questions about the current state and the previous state. Keep work-item status in the work-item record. Consider a graph backend if evaluation shows that multi-entity or multi-hop questions defeat simpler retrieval. [Graphiti temporal semantics](https://help.getzep.com/searching-the-graph#datetime-filtering), [Raphie memory evidence](../../CONTEXT.md), [Raphie storage](../../apps/docs/src/content/docs/architecture/state.mdx).

## Mem0

**Component and maturity.** Mem0 is an embeddable memory library and a self-hostable memory server. GitHub displayed about **69.5k stars**, Apache-2.0, and Node SDK **3.3.1** in the latest-release view. The library wires an LLM, embedder, vector store, optional reranker and history store. Its documented Python defaults are local Qdrant and SQLite history. The Docker server uses PostgreSQL with pgvector by default. The hosted Platform offers a separate deployment choice. [Repository](https://github.com/mem0ai/mem0), [Node SDK release](https://github.com/mem0ai/mem0/releases/tag/ts-v3.3.1), [open-source architecture](https://docs.mem0.ai/open-source/overview), [hosted API](https://docs.mem0.ai/platform/quickstart).

**Chat, context and work.** The caller provides messages at ingestion and chooses scoping with user, agent and run identifiers. The identifiers filter memory and can span whichever chats the app chooses. The documented integration is an add/search loop. The app owns the canonical chat, compaction and verbatim tail, retrieval placement and prompt caching, and the schedule and work-item UI. The async client can move memory work off the reply path if the caller schedules it. Mem0's stored memory history is a record of memory changes. Use the app's transcript to recover the conversation itself. [Open-source overview](https://docs.mem0.ai/open-source/overview), [scope implementation](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py#L290-L348), [async ingestion](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py#L2239-L2255), [memory change history](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py#L3329-L3341).

**Memory and freshness.** In the inspected Python `main` path, `add(infer=True)` retrieves candidates as context for a single extraction request, embeds extracted memory text and deduplicates by hash before writing. `infer=False` stores supplied messages directly. Query-time search combines vector and keyword candidates where supported and can rerank the result. Explicit update, delete and history methods let a caller correct a memory and inspect changes. The current extraction path is additive. A caller that needs a hard guarantee that a superseded fact disappears from current retrieval must verify its explicit correction policy. That guarantee does not follow from deduplication. [Add and deduplication source](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py#L805-L980), [search source](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py#L1496-L1565), [memory mutation and history source](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py#L1664-L1800).

**Raphie takeaway.** Use Mem0 as a benchmark for a scoped fact store with optional extraction. Compare it with Raphie's SQLite evidence store on recall of exact details, correction of preferences, write cost, and traceability to the owner's words. Its value would come from improving evidence retrieval. Compaction and concurrent work still require runtime changes. [Mem0 open-source overview](https://docs.mem0.ai/open-source/overview), [Raphie domain model](../../CONTEXT.md), [Raphie storage](../../apps/docs/src/content/docs/architecture/state.mdx).

## Comparison

| Project        | Chat model                                                               | How it bounds model context                                                                 | How concurrent work reaches the user                                                                                                                                                                                                                                                                                                                                             |

## Lessons for Raphie

1. **Build the work-item record first.** Give every item a stable ID, source message or handoff, status, notes and latest result. Link schedules and background sessions to it where applicable. Put a compact list of open titles, statuses and IDs into chat context, with a tool to fetch details and an owner-visible Work page. Let the bot and owner update work through the durable record. Keep small requests in the chat when they settle within the turn. Start with one durable request and its follow-up, then verify it survives chat compaction, restart and rewind. Ensure an item closed during a background run stays closed when the late result arrives. [Raphie work items and rewind](../../CONTEXT.md), [OpenClaw automation lifecycle](https://docs.openclaw.ai/automation/cron-jobs/how-it-works), [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence).
2. **Keep background execution out of the main chat's prompt.** Give long-running work a context seeded from its work item and a small excerpt from the originating chat. Use one background session for a work item while it stays open, as the domain already specifies. Send meaningful progress, questions or the result back through the chat, using a quote and linked artifact. Record delivery against the run so restart can reconcile it without duplicate replies. For monitoring, use per-job state and a quiet outcome when nothing changes. [Raphie work items, quotes and delivery](../../CONTEXT.md), [OpenClaw child execution and delivery](https://docs.openclaw.ai/automation/cron-jobs/payloads), [OpenClaw requester delivery](https://docs.openclaw.ai/tools/subagents/announce).
3. **Make compaction reversible at the point of recall.** Keep the existing 64k working threshold and scaled recent tail for an initial test. Give important summary entries stable message references or source ranges. Add bot-scoped transcript search with exact IDs and links, followed by a bounded surrounding excerpt. An active-history search should respect rewind, while explicit inspection can show rewound messages with their status. Test dates, URLs, corrections, interleaved commitments and tool call/result boundaries after several compactions. Begin with keyword search and source pointers. Evaluate hierarchical summaries if older episodes still become difficult to find. [Raphie summary policy](../../apps/docs/src/content/docs/architecture/execution.mdx#summarizing-long-sessions), [Raphie rewind](../../CONTEXT.md), [OpenClaw cut rules](https://docs.openclaw.ai/reference/session-management-compaction/compaction), [Lossless Claw source links](https://github.com/Martian-Engineering/lossless-claw/blob/main/docs/architecture.md), [Letta recall](https://docs.letta.com/v1-sdk/concepts/stateful-agents).
4. **Measure the cost of the request actually sent.** Track uncached input, cached input, cache writes, summary calls, retrieval calls and overflow retries per completed owner turn. Compare the current policy against earlier offloading of bulky tool output, then test compaction timing on providers with warm caches. Preserve the stable prompt prefix where the provider's cache permits it. Change the policy only if a test using several interleaved work items shows savings while maintaining recall and latency. [Raphie compaction telemetry](../../apps/docs/src/content/docs/architecture/execution.mdx#summarizing-long-sessions), [OpenClaw session pruning](https://docs.openclaw.ai/concepts/session-pruning), [OpenClaw warm compaction](https://docs.openclaw.ai/concepts/compaction#warm-request-compaction), [Deep Agents offloading](https://docs.langchain.com/oss/python/deepagents/context-engineering#offloading).
5. **Consolidate memory with provenance and explicit supersession.** Try a bounded background review after compaction or an idle interval. Review only new eligible evidence since a durable cursor. Require a source message and the prior record's revision for any proposed replacement, and keep older versions available for historical recall. Attribute scheduled observations to the job that produced them. Let updates to owner instructions continue through Raphie's existing mechanism. Evaluate forgotten facts, stale retrieval, mistaken promotions and the added model cost before trying a separate memory service. [Letta dreaming](https://docs.letta.com/configuration/memory), [Khoj automation write gate](https://github.com/khoj-ai/khoj/blob/master/src/khoj/processor/conversation/utils.py#L557-L575), [Graphiti validity](https://help.getzep.com/v4/facts), [Raphie instructions and memory evidence](../../CONTEXT.md).
