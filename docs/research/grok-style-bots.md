# Grok-style bots and long-running chat

Research snapshot, 26 November 2026. GitHub counts and versions are approximate snapshots. The findings come from public documentation, release notes and source inspection. I did not run the products or measure their costs.

## Summary

- **Grok Bot is xAI’s persistent work teammate.** It has a continuing direct chat, separate group or team contexts, managed memory, routines that report into chat, and a Tasks pane for delegated coding runs. Grok Chat’s Automations start a new conversation for each run. Grok’s animated Companions were a separate feature. [Grok Bot launch](https://x.ai/news/introducing-grok-bot) · [Bot changelog](https://x.ai/changelog/bot) · [Grok Chat Automations](https://x.ai/news/grok-automations) · [Ofcom’s record of the standalone Companions](https://www.ofcom.org.uk/online-safety/illegal-and-harmful-content/ofcom-update-monitoring-xs-response-to-hate-and-terror-content-and-grok-investigation-latest)
- **Codync is the closest open-source work reference.** It keeps one private transcript per bot while separate, queued work runs in its own sessions. It offers distinct semantics for one-off follow-ups and recurring work, with approvals and results in chat. Nightly Labs’ OpenBot goes further on parallel work and bounded context transfer. Its current license permits noncommercial use. [Codync conversations](https://www.codync.dev/docs/conversations#work) · [Codync routines](https://www.codync.dev/docs/routines) · [OpenBot agent architecture](https://github.com/nightly-labs/openbot/blob/main/docs/architecture/agents.md) · [OpenBot license](https://github.com/nightly-labs/openbot/blob/main/LICENSE)
- **Raphie already has the right continuity primitives.** Keep the transcript, summary, memory evidence, and live work-item state independently addressable. The strongest additions to evaluate are bounded transcript recall, cache-aware compaction measurements, and concise updates linked to the originating request and work item. [Raphie’s chat ADR](../adr/0001-one-chat-per-bot-with-work-items.md) · [Raphie’s compaction policy](../../apps/docs/src/content/docs/architecture/execution.mdx#summarizing-long-sessions) · [Codync context and memory](https://github.com/leepokai/Codync/blob/main/docs/features/context-and-memory.md)

## xAI — Grok Bot and the other Grok surfaces

**Product and maturity.** xAI launched Grok Bot in beta on 11 August 2026. It is a hosted product for individuals and teams, with v1.3.0 released 24 November. Thin chat clients connect to Cursor’s service, which gives each user a Firecracker microVM. That user’s bots share its persistent workspace and sign-ins, and each has its own screen. The service exposes connected apps through its connector backend, along with browser and desktop tools and local computer access under explicit approval. Conversation history lives outside the shared computer. xAI says the service chooses a model per task and can route to first- or third-party models. Public documentation describes these boundaries and leaves the underlying storage engine and executor private. [Launch](https://x.ai/news/introducing-grok-bot) · [November releases](https://x.ai/changelog/bot) · [Architecture](https://docs.x.ai/grok-bot/teams-and-enterprises#architecture) · [Computer and apps](https://docs.x.ai/grok-bot/computer-and-apps) · [Security and privacy](https://docs.x.ai/grok-bot/approvals-security-and-privacy) · [FAQ](https://docs.x.ai/grok-bot/faq)

**Chat and work.** The default interaction is a direct message to a named bot, continued across devices. Eligible personal accounts can reach the same bots through X Chat. There are also group chats and shared Team Bots. The enterprise hook’s `session_id` identifies the bot across chats and members, so it provides no evidence that all messages use one model session. A direct message can redirect ongoing work and has priority over background work. Bots can coordinate with other bots, post approval and draft cards, and publish an artifact card with a link to the bot’s Library. Routines support schedules and triggers such as Slack, email and webhooks. They run in the cloud, can read earlier messages in their chat, and can post results there. The routine detail shows run status and failure reasons. The primary bot can proactively offer work or flag a disconnected app. The desktop **Tasks** pane tracks delegated coding Cloud Agents, with status in the pane and the exchange and returned artifacts in the chat. Larger coding requests can launch a Project whose Cloud Agent plans and delegates work. Across bots, reasoning and tool work can run in parallel. One bot can drive one computer-use task on its screen at a time. Background approvals expire after about 30 minutes. I did not find an equivalent documented durable list for arbitrary open commitments, or a per-bot scheduler specification. [Chat and collaboration](https://docs.x.ai/grok-bot/chat-and-collaboration) · [Inference hook fields](https://docs.x.ai/grok-bot/inference-hooks) · [Routines](https://docs.x.ai/grok-bot/skills-routines-and-automations) · [Approvals](https://docs.x.ai/grok-bot/approvals-security-and-privacy) · [Files and Cloud Agent results](https://docs.x.ai/grok-bot/files-and-results) · [Tasks pane and routine context](https://x.ai/changelog/bot) · [Initiative](https://docs.x.ai/grok-bot/initiative) · [Concurrency FAQ](https://docs.x.ai/grok-bot/faq)

**Context and cost.** The enterprise inference-hook contract confirms that Grok Bot writes a summary that replaces older messages in the model-facing conversation. It covers model calls that write summaries and excludes ancillary memory saves. It also shows rules and shared memory reaching the model as context. xAI does not document the Bot’s thresholds, recent-message window, summary template, retrieval ranking or prompt-cache policy. Usage attribution by bot and source and account spending controls are documented. The separate Grok API cookbook gives evidence for stable-prefix caching and shows a short benchmark where frequent compaction cost more than it saved. Its demo thresholds, encrypted compaction item and pricing apply to that API example. [Inference hooks](https://docs.x.ai/grok-bot/inference-hooks#coverage) · [Usage settings](https://docs.x.ai/grok-bot/settings-and-notifications) · [Grok API caching example](https://docs.x.ai/cookbook/examples/prompt-caching)

**Memory.** Personal bots decide when to save durable facts, preferences, rules and dated work notes. The November changelog describes separate memories for people and organizations, the owner profile, standing instructions and projects. You can also ask a bot to remember, correct or forget a fact. Some owner facts, such as name and time zone, are shared across bots. A bot can recall information from its other chats and voice calls, including in a group chat. A personal bot exposes memory through chat. Resetting a conversation preserves the bot’s memory. Team Bot memory has approval rules for shared learning. The docs establish automatic decisions and separate model calls for saves, but leave exact triggers and internal storage undisclosed. [Bot memory and lifecycle](https://docs.x.ai/grok-bot/bots#what-a-bot-remembers) · [November changelog](https://x.ai/changelog/bot) · [Inference hooks](https://docs.x.ai/grok-bot/inference-hooks#coverage)

**Related surfaces.**

- **Grok Chat on grok.com and mobile** advertises recall of preferences and past chats. Its Automations, announced July 2026, run on a schedule or matching incoming email. Each run is a fresh, resumable conversation with a saved run entry and configurable notifications. Its published memory and automation behavior gives no implementation details for recall or compaction. [Grok Chat](https://x.ai/grok?q=Tesla+ai+computer) · [Automations launch](https://x.ai/news/grok-automations)
- **Grok on X** includes the Grok interface in X, the public `@Grok` account, and Grok interactions in X Chat. X documents personalization controls and chat-history deletion. Its help also distinguishes asking Grok about a selected message from adding Grok as a chat member. The rollout of personal Grok Bots into X Chat is documented separately. [X’s parliamentary submission](https://docs.publicnow.com/viewDoc?filename=31335%5CEXT%5CBC2841F63D5AEB029D4430CA8A10ADA92D396588_D3FDF120F894BC14A307F6270A0C42379E4ABF4B.PDF) · [X’s Grok help](https://help.x.com/en/using-x/about-grok) · [X Chat help](https://help.x.com/en/using-x/about-chat) · [Grok Bot in X Chat](https://docs.x.ai/grok-bot/chat-and-collaboration#chat-in-x-chat)
- **Grok Companions** included animated character personas. I could verify Ani as a historical standalone Grok feature from Ofcom’s account of its direct engagement with xAI. I found no current xAI documentation confirming the companion roster, memory, sessions, scheduling or exact retirement date. The old Grok Ani and Valentine URLs returned 404. Animation Inc publishes the separate Animates app. Its public landing page establishes the app’s identity but does not substantiate any history or memory migration from Grok. [Ofcom’s account](https://www.ofcom.org.uk/online-safety/illegal-and-harmful-content/ofcom-update-monitoring-xs-response-to-hate-and-terror-content-and-grok-investigation-latest) · [Animates](https://animates.ai/)
- **Grok Build** documents background memory capture after completed turns, Markdown notes scoped to the project and user, and periodic consolidation into topics. It explicitly excludes task state from long-term notes. This is evidence about the coding harness. [Grok Build memory](https://x.ai/news/grok-build-memory)

**For Raphie.** Reuse the behavior of reporting a named job’s meaningful results and requests for input in the chat. Keep the Work page as the place to find execution state and run history. Grok Chat’s per-run conversations would make the owner manage the same work in two places. ## Codync — an open-source Grok Bot alternative

**Product and architecture.** Apache-2.0, roughly 2.5k stars, with v2.53.0 released 22 November. Codync targets developers running their own coding harnesses. A Rust host drives agents through the Agent Client Protocol (ACP), owns the SQLite transcript and queue, and serves desktop, phone and terminal clients. Agents run with their own provider authorization, within the bot’s configured workspace and permission policy. The host also provides MCP tools for bot collaboration, memory and routines. [Canonical repository](https://github.com/leepokai/Codync) · [Releases](https://github.com/leepokai/Codync/releases) · [Source layout](https://github.com/leepokai/Codync/blob/main/docs/architecture/file-structure.md)

**Chat, context and cost.** The bot’s private chat stays in SQLite across ACP sessions. Replies quote the relevant message in the same chat. Each request sends new input to the harness, which maintains the rolling context and writes its summaries. The host’s default Auto setting leaves compaction to the harness. With host thresholds enabled for Claude Code and Codex, Codync can request a summary near the limit or at a configured size. The code’s baseline policy uses the smaller of 75% of the context window and 200k tokens. Its idle path targets inputs of at least 100k tokens during the last five minutes of an observed one-hour cache. A cold large prompt, eight hours away after three compactions, or repeated ineffective compaction can lead to a fresh session. The rollover has an editable handoff with the prior summary, recent requests, last reply, plan and a history bookmark. The keep-list asks for exact identifiers, owner constraints, decisions and the next step on open work. Stable instruction snapshots and update blocks keep the prefix steady between compactions. Public docs leave the verbatim suffix and summary detail to the chosen harness. [Context and memory](https://github.com/leepokai/Codync/blob/main/docs/features/context-and-memory.md) · [Compaction policy source](https://raw.githubusercontent.com/leepokai/Codync/main/host/crates/memory/src/compaction.rs) · [Fresh conversations](https://www.codync.dev/docs/conversations#fresh-conversations)

**Parallel work and scheduling.** The bot puts long work into a queue and runs a configurable number of separate sessions. Its Work affordance shows active, waiting and recent work. Questions, approval cards, reports and artifacts surface in the private chat with the job’s title. Details can open a work session’s steps and, when enabled in a Git project, concurrent work can get its own worktree. A one-time follow-up runs back in the private chat and can stay silent if nothing changed. A routine can be scheduled or triggered, normally runs in a fresh session with its prompt, instructions, memory and a replaceable progress note of up to 2,000 tokens, and reports into chat. A run can be quiet on success, and an explicit failure is visible. [Work and follow-ups](https://www.codync.dev/docs/conversations) · [User guide to routines](https://www.codync.dev/docs/routines) · [Routine implementation notes](https://github.com/leepokai/Codync/blob/main/docs/features/routines.md)

**Memory.** Bot and shared scopes use Markdown facts and longer notes, with provenance and versions in SQLite. The initial prompt carries the short facts and note index. MCP tools can read, edit and do substring searches. `search_history` retrieves by text or message ID, with paged results independently of semantic memory. The documented background review checks new owner messages after an idle interval or a message-count trigger, and before some session transitions. The model proposes edits with supporting user quotes. The host checks provenance, scope and what a background turn may change, and records versioned updates. [Context and memory](https://github.com/leepokai/Codync/blob/main/docs/features/context-and-memory.md)

**For Raphie.** Borrow the history bookmark, explicit confirmation of a scheduled check, and approval and result links in chat. Keep Raphie’s existing Work page and avoid requiring the owner to open a work session. A small structured checkpoint for a recurring job is easier to bound and verify than carrying forward everything its previous runs saw. [Codync conversations](https://www.codync.dev/docs/conversations) · [Codync routine progress](https://www.codync.dev/docs/routines#progress-from-one-run-to-the-next) · [Raphie’s chat ADR](../adr/0001-one-chat-per-bot-with-work-items.md)

## OpenBot by Nightly Labs — a source-available work comparison

**Product and architecture.** Roughly 11.1k stars and releasing actively, with v0.79.0 marked latest at review. Nightly Labs’ current code is PolyForm Noncommercial 1.0.0. Its project says releases through 0.1.11 remain Apache-2.0. It is a local-first desktop workspace with optional hosted or joined servers, native harness adapters such as Claude, Codex and Grok, local SQLite data, and OpenBot tools for work, memory and handoffs. The provider adapter owns model-specific calls. The host owns mailboxes, dispatch, event projections and the public chat. [Repository and licensing notes](https://github.com/nightly-labs/openbot#license) · [Releases](https://github.com/nightly-labs/openbot/releases) · [Provider architecture](https://github.com/nightly-labs/openbot/blob/main/docs/architecture/providers.md) · [Host architecture](https://github.com/nightly-labs/openbot/blob/main/docs/architecture/servers.md)

**Chat, context and cost.** Each agent has a main chat and user-visible side threads. The host also supports channels with separate access and history. The agent can search its allowed chat history and read excerpts by thread. Claude compacts natively. The host can request compaction for supported native adapters. Codex uses 80% of the reported context window. For Antigravity the host rotates the provider session under the same public chat and passes a history handoff. The providers retain their own summary behavior and window rules. The Claude adapter keeps the cacheable system prompt stable, sending the full selected memory block on the first turn or after compaction and subsequent changes with user input. [Agents and history](https://github.com/nightly-labs/openbot/blob/main/docs/architecture/agents.md) · [Compaction ownership](https://github.com/nightly-labs/openbot/blob/main/docs/architecture/providers.md#compaction-ownership) · [Memory delivery](https://github.com/nightly-labs/openbot/blob/main/docs/architecture/team-api.md)

**Parallel work and scheduling.** The agent can start a side thread with `start_task` and the owner can open or branch one. Threads have separate sessions, queueing and cancellation, while prompts and approvals reach the main chat. Desktop and web expose side-thread tabs. A routine can use a persistent user-visible thread but start an ephemeral provider session for each run. That session gets up to 8,000 characters of recent routine and chat excerpts. A non-quiet run contributes a digest of up to 1,500 characters to the next main-chat prompt, capped at 6,000 characters across pending digests. The chat shows the run marker and links to the result thread. The scheduler can wake an existing wait with an event without repeating the routine’s work. [Agent architecture, routine sessions and side threads](https://github.com/nightly-labs/openbot/blob/main/docs/architecture/agents.md)

**Memory.** OpenBot stores agent memories in SQLite. A selected essential subset uses a bounded startup block (8,192 UTF-8 bytes). Other entries are available through bounded local FTS5/BM25 search and paginated recall. The agent can call memory tools. Background review defaults to 20 completed turns or 15 minutes of idle time with at least three new turns. Clearing a chat or closing a changed side thread can trigger it too. Channels and routine runs are excluded from the review counter. The review counter and cursor are process-local. The host can also promote a learned procedure to a skill. [Memory storage and retrieval](https://github.com/nightly-labs/openbot/blob/main/docs/architecture/team-api.md) · [Background review](https://github.com/nightly-labs/openbot/blob/main/docs/architecture/providers.md#background-memory-review)

**For Raphie.** The compact result digest and the rule for preserving an update that arrives while the chat turn starts are worth studying. Preserve Raphie’s work-item identity and chat result link. Using side-thread tabs or copying broad chat excerpts into every scheduled run would add navigation and context cost. [OpenBot agent architecture](https://github.com/nightly-labs/openbot/blob/main/docs/architecture/agents.md) · [Raphie’s chat ADR](../adr/0001-one-chat-per-bot-with-work-items.md)

## Utsuwa — an open-source Grok Companion alternative

**Product and architecture.** A local-first animated companion for personal chat and voice, with optional relationship mechanics. Roughly 156 stars, v0.21.4 released 7 November, and the desktop app remains beta. Current code is AGPL-3.0-or-later. The SvelteKit browser app and Tauri desktop app pair a VRM avatar with configurable model, voice and optional MCP providers. IndexedDB stores turns, session records, relationship state and memories on the device. [Repository and license](https://github.com/JuiceBoxxGames/utsuwa) · [Releases](https://github.com/JuiceBoxxGames/utsuwa/releases) · [Companion architecture](https://docs.utsuwa.ai/technology/companion-system)

**Chat, context and cost.** One companion experience spans app launches, with one stored session per app run. The owner can inspect saved sessions in Settings. An in-memory history buffer reloads the most recent 20 turns, with 10 returned by the retrieval path when context scaling is off. Optional scaling injects 6, 10 or 20 recent turns and 3, 5 or 10 relevant facts depending on the configured window. It trims history before each model or tool round to leave a 500-token reply reserve. On a later load, unsummarized sessions get a deterministic summary based on frequent topics. The latest eligible past-session summary can appear after more than six hours away. The ordinary summary path requires no model call. Missing structured output on an eligible chat path can trigger an extra extraction call. I found no provider prompt-caching policy. [Memory inspector and session history](https://docs.utsuwa.ai/guides/memory) · [Context and response parsing](https://docs.utsuwa.ai/technology/companion-system) · [Retrieval source](https://raw.githubusercontent.com/JuiceBoxxGames/utsuwa/main/src/lib/engine/memory.ts)

**Work and memory.** The companion can schedule timers and reminders for itself. The bell lists fired and missed timers. A timer due while closed is marked missed, which makes this a useful reminder interface but weak evidence for always-on work. The app can capture one fact from the model’s reply metadata and supplements it with pattern extraction. It deduplicates same-category facts by normalized text or cosine similarity of at least 0.9. Before replying it ranks up to 500 candidate facts using local multilingual embeddings and importance, with a keyword and high-importance fallback. The owner can inspect, add or delete notes. A correction in chat can leave the old fact in place. [Timers and storage](https://github.com/JuiceBoxxGames/utsuwa#features) · [Memory behavior](https://docs.utsuwa.ai/guides/memory) · [Deduplication design](https://docs.utsuwa.ai/technology/companion-system#deduplication)

**For Raphie.** Test whether small, automatic recall improves answers on older references. Keep Raphie’s explicit revision and provenance semantics, since matching similar text alone cannot decide whether the owner corrected a fact or described a second one. Frequent-topic summaries can help label old history, but cannot reliably carry a commitment or its exact deadline. [Utsuwa’s memory architecture](https://docs.utsuwa.ai/technology/companion-system) · [Raphie memory](../../apps/docs/src/content/docs/guides/memory.mdx)

## Project AIRI — an open-source animated companion

**Product and architecture.** MIT, roughly 51.8k stars, with v0.15.5 published as a pre-release on 14 November. AIRI describes itself as a self-hosted Grok Companion inspired by Neuro-sama. It uses a shared Vue/TypeScript stage, a web and Electron desktop experience, optional hearing and speech providers, MCP tools and separate integrations such as Discord and Minecraft. The desktop keeps chat sessions in local IndexedDB and has an optional cloud history path. [Repository](https://github.com/moeru-ai/airi) · [Releases](https://github.com/moeru-ai/airi/releases) · [Stage architecture](https://github.com/moeru-ai/airi/blob/main/packages/stage-ui/README.md) · [Desktop chat storage fix](https://github.com/moeru-ai/airi/issues/2087)

**Chat, context and cost.** Each chat session belongs to a character and the interface provides a session list. The source documentation describes an off-by-default Conversation Compact experiment. A soft byte estimate schedules a summary of older observations. Background mode keeps sending requests while the summary runs. Synchronous mode waits for an already triggered summary. The provider still decides whether an uncompacted request fits. I found no documented provider cache policy or stable contract for what the summary preserves. [Stage architecture and experimental features](https://github.com/moeru-ai/airi/blob/main/packages/stage-ui/README.md)

**Work and memory.** AIRI ships tool and game integrations. Its stage docs describe a cloud inbox for account notifications. I found no documented equivalent of a persistent work-item queue or a recurring job scheduler that reports into one chat. An author devlog demonstrated cross-session recall in FlowChat as a memory-layer experiment. AIRI’s manual describes configurable long-term memory and cautions that it is evolving, while the repository marks Alaya as work in progress. The sources do not establish a stable general-purpose save and retrieval policy for the shipped companion. [Stage tools and inbox](https://github.com/moeru-ai/airi/blob/main/packages/stage-ui/README.md) · [FlowChat experiment](https://airi.moeru.ai/docs/en/blog/DevLog-2026.01.01/) · [Tamagotchi manual](https://github.com/moeru-ai/airi-docs/blob/main/content/en/docs/manual/tamagotchi/setup-and-use/index.md) · [Repository roadmap](https://github.com/moeru-ai/airi#current-progress--roadmap)

**For Raphie.** AIRI’s asynchronous compaction supports the same responsiveness goal as Raphie’s existing background threshold. Raphie should retain its blocking path for model limits. The visible session list and notification inbox offer little for keeping work discoverable through one chat. [AIRI compaction experiment](https://github.com/moeru-ai/airi/blob/main/packages/stage-ui/README.md#experimental-features) · [Raphie execution](../../apps/docs/src/content/docs/architecture/execution.mdx#summarizing-long-sessions)

## Lessons for Raphie

1. **Make the work item the authoritative answer to “what’s still going on?”** Include its stable ID, title, state and latest result or next dependency in the chat turn’s work-item list. Match a quote to the originating work item so “any update on this?” can route to its existing background session. Keep result, approval and question cards in chat, with the full item on Work. The existing ADR already establishes that owner interaction model. [Raphie’s chat ADR](../adr/0001-one-chat-per-bot-with-work-items.md) · [Codync work and quotes](https://www.codync.dev/docs/conversations)
2. **Add bounded transcript recall alongside the session summary.** Start with exact message IDs and lexical lookup for names, dates, links and identifiers. Return a small set of snippets with source pointers and distinguish rewound entries. Test a follow-up about an old quoted request after several compactions. Durable work state should come from the work item and factual memory should continue through its own revision and provenance rules.
