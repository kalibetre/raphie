Raphie has one administrator, created from a terminal on the machine that runs it. Every page, API call, download and event stream in the web workspace requires that administrator to be signed in. Creating the account and resetting its password only work locally; neither is reachable over HTTP.

Sign-in is built on [Better Auth](https://better-auth.com), which owns password hashing, sessions and password reset.

## Create the administrator

Until an administrator exists, the web host is **locked**. The sign-in page explains how to unlock it, and everything else is refused.

<Steps>

1. Start Raphie.

2. On the same machine, run the setup command for your install:

   ```sh
   raphie auth setup              # user install
   sudo raphie auth setup         # Linux system service
   bun run raphie auth setup      # source checkout
   ```

   On the system service, the command runs as the `raphie` service user, so the files it creates stay readable by the service.

3. Enter an email, then a password of at least 12 characters, twice. The password is never echoed, logged or accepted as an argument or environment variable.

4. Open your Raphie address and sign in. By default that is `http://127.0.0.1:24320` for a user install, `http://127.0.0.1:41837` for the system service and `http://127.0.0.1:4320` for a source checkout; `raphie port` prints yours.

</Steps>

A second `setup` is refused. The database also allows only one user, so two racing setup commands still create one account.

Add `--data-dir PATH` to `setup` or `recover` when Raphie's data is not in the default location. The command must run as the account that owns the data directory.

## Recover access

If you forget the password, or think a password, passkey or device is compromised, run recover on the Raphie machine:

```sh
raphie auth recover            # sudo raphie auth recover on a Linux system service
```

It prompts for a new password and then:

| Effect                               | Detail                                  |
| ------------------------------------ | --------------------------------------- |
| Changes the password                 | Through Better Auth's reset flow        |
| Signs out every browser and device   | All sessions, including device sessions |
| Removes every passkey                | Register them again after signing in    |
| Invalidates outstanding device codes | Devices must start sign-in again        |
| Clears sign-in attempt limits        | Lets you sign in right away             |

`recover` also completes a half-finished setup. It needs local access to the data directory and has no HTTP equivalent.

## Passkeys

Register passkeys in **Settings → Account**. Password sign-in keeps working alongside them.

- Registering needs a fresh browser session. If yours has aged out, sign in again first.
- A passkey belongs to one hostname. Register separately for `localhost`, a Tailscale name or a custom domain; a passkey for one cannot sign in to another.
- Use `http://localhost:PORT` for local passkeys, not `127.0.0.1`. Numeric addresses are not portable passkey hosts.
- Only a signed-in browser can add or remove passkeys. Device sessions cannot.

## Connect a native device

The [desktop app](/guides/desktop/) signs in with a device code: the device shows a short code and a link, and you approve it in a browser where you are already signed in.

      steps: [["Device", "Web host", "Poll for a token"]],

    ["Web host", "Device", "Device session token (30 days)", "reply"],
  ]}
/>

<Steps>

1. Start sign-in on the device. It shows a code and an approval link.

2. Open the link in a browser signed in to Raphie. The link must contain the code; opening `/device` on its own sends you back to the device.

3. Compare the code on the page with the one on the device in front of you, then choose **Approve** or **Deny**.

</Steps>

:::caution[Approve only codes you started]
An approved device gets full access to the web workspace. A device's name is a claim, not proof of identity. Never approve a code someone sent you.
:::

| Device sign-in fact      | Value                                                    |
| ------------------------ | -------------------------------------------------------- |
| Code lifetime            | 10 minutes                                               |
| Minimum polling interval | 5 seconds                                                |
| Session length           | 30 days, separate from any browser session               |
| Where it is listed       | **Settings → Account**, by name; tokens are never shown  |
| Disconnecting            | Takes effect on the next request and closes open streams |

The desktop app keeps its token in the operating system's credential store.

## Sessions

| Setting         | Value                                                                          |
| --------------- | ------------------------------------------------------------------------------ |
| Lifetime        | 30 days, refreshed daily while in use                                          |
| Cookie          | `HttpOnly`, `SameSite=Lax`, named per web port (`raphie_<port>.session_token`) |
| `Secure` cookie | On HTTPS origins only; loopback HTTP cookies are not `Secure`                  |
| Revocation      | Immediate: every request re-reads the session from the database                |
| Event streams   | Re-checked every 2 seconds and closed when their session ends                  |

Use the account menu beside the sidebar's connection status to open **Manage account** or **Sign out**. Signing out ends only the current browser's session.

## What is protected

The check runs in front of the application in both the production host and the development server. There is no bypass, including in the test fixture.

| Request                                                     | Requirement                                                       |
| ----------------------------------------------------------- | ----------------------------------------------------------------- |
| Pages, server functions, `/api/*`, downloads, event streams | A signed-in browser session or an approved device session         |
| Browser requests that change state                          | Also an `Origin` that matches the configured origin               |
| Passkey management, device approval, connected devices      | A signed-in browser session from the same origin                  |
| `/login`, built `/assets/*`                                 | Public                                                            |
| `GET /_raphie/health`, `GET /auth/status`                   | Public; report `ready` or `locked` and whether you are signed in  |
| Password and passkey sign-in, sign-out                      | Public once an administrator exists                               |
| Device code request and token polling                       | Public once an administrator exists; browser credentials rejected |

Every request must also use a configured host; anything else gets `403`. When a request is refused, a page load redirects to `/login`, an API call gets `401`, and a locked host answers `503`. If the authentication store cannot be checked, the request is refused with `503`, never let through.

## Storage and backups

| File          | Holds                                                         | Mode   |
| ------------- | ------------------------------------------------------------- | ------ |
| `auth.sqlite` | The administrator, password hash, sessions, passkeys, devices | `0600` |
| `auth.secret` | The key that signs session cookies                            | `0600` |

Both live in the data directory, so your normal [backups](/operate/backup-and-recovery/) include them. Protect those backups: they contain the password hash, live session tokens and the signing key.

- Restoring a backup restores the administrator, password and sessions as they were. Run `raphie auth recover` afterwards if any of that is in doubt.
- If `auth.secret` is lost, Raphie creates a new one. Everyone signs in again, and device sessions and pending device codes are invalidated.
- A malformed `auth.secret`, or one readable by group or others, stops the web host instead of being replaced.
- The schema migrates automatically on start, so upgrades keep the administrator and sessions.

## Limits

- **One administrator.** Multiple users are not supported.
- **The runtime port is not authenticated.** Sign-in protects the web host. The runtime port (`24316` on a user install, `4316` otherwise by default) trusts any local process that reaches it; see [security](/architecture/security/).
- **Duplicate-guess throttling only.** Each email and password pair gets five attempts per minute; other authentication calls share a limit of 60 per minute. This does not stop distributed or varied-password guessing. Limit who can reach Raphie with tailnet access rules.
- **Forwarded headers are ignored.** Raphie never trusts client-address headers. The web host listens on loopback only; reach it remotely through a TLS proxy that preserves the configured host. See [remote access](/operate/remote-access/).
