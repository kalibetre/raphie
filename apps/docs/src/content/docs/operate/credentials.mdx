Raphie encrypts every saved credential before it reaches disk. The databases hold only ciphertext; the key that decrypts it lives somewhere else: your operating system's credential store, or an owner-only file on a headless Linux host. Copying the data directory alone does not reveal your keys.

## What is encrypted

You enter credentials in Settings. Raphie encrypts them with AES-256-GCM in each bot's databases.

| Credential                                            | Where you enter it       | What is encrypted                               |
| ----------------------------------------------------- | ------------------------ | ----------------------------------------------- |
| Model provider API keys                               | **Settings → Providers** | Each key on its own, in `settings.sqlite`       |
| Subscription sign-in tokens (access, refresh, expiry) | **Settings → Providers** | Each token set on its own, in `settings.sqlite` |
| Hindsight memory API key                              | **Settings → Memory**    | The key, in `memory.sqlite`                     |
| MCP connection secrets and OAuth tokens               | **Settings → MCP tools** | The whole connection list, in `mcp.sqlite`      |
| Channel tokens, such as a Telegram bot token          | **Settings → Channels**  | The whole channel configuration                 |

Provider names, defaults and other settings are stored in plain form. Credentials never appear in browser responses, conversations, session choices or Activity; error messages and logs redact them.

## Where the master key lives

Each database that holds credentials records only a non-secret key ID. With the OS store, every such database gets its own random 256-bit key, saved under service `com.raphie.provider-credentials` and named by that key ID. With a key file, every database uses the one 256-bit key in the file.

| Platform                      | Master key store                                                                         | What it needs                                                             |
| ----------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| macOS                         | Login Keychain, service `com.raphie.provider-credentials`                                | An unlocked login session. macOS may ask you to allow access.             |
| Linux desktop                 | Secret Service (GNOME Keyring, KWallet) via libsecret                                    | libsecret installed and an unlocked keyring in the runtime user's session |
| Linux system service          | GNOME Keyring in a private session, unlocked at start by a host-bound systemd credential | Installed and configured by the system installer                          |
| Headless Linux (user install) | An owner-only master key file                                                            | `install.sh --headless`, or `RAPHIE_CREDENTIAL_KEY_FILE`                  |

Raphie never falls back from one store to another. If `RAPHIE_CREDENTIAL_KEY_FILE` is set, it uses the file; if not, it uses the OS store.

### Headless hosts: the master key file

A server with no desktop session has no unlocked keyring. For those, point Raphie at a file instead.

<Tabs>
<TabItem label="Installer">

```sh
bash install.sh --headless
```

Linux only, with a systemd user manager. The installer creates `~/.local/share/raphie-headless/master-key` and sets it on the Linux user service. It refuses to switch an installation whose settings are already encrypted with another store.

</TabItem>
<TabItem label="Manual">

Set `RAPHIE_CREDENTIAL_KEY_FILE` to an absolute path outside the data directory. Raphie creates the file, and its directory if missing, the first time a database needs a key.

</TabItem>
</Tabs>

The file is checked on every start:

| Rule           | Requirement                                                                         |
| -------------- | ----------------------------------------------------------------------------------- |
| Location       | An absolute path outside the data directory; the runtime refuses to start otherwise |
| Directory      | Owned by the runtime user, mode `0700`                                              |
| File           | A regular file owned by the runtime user, mode `0600`, one 256-bit key in base64    |
| Links          | Symbolic links and hard-linked keys are refused                                     |
| Existing files | Never overwritten, even when malformed                                              |

The path is the only setting. The key itself is never an environment variable. This mode relies on file permissions alone, so anyone who can read both the key file and the databases can decrypt the credentials.

## When the store is locked or missing

Raphie reads the master key once at start and keeps it in memory until it stops.

- **Locked, denied or unavailable at start:** the runtime does not start. It prints one fixed message telling you to unlock the store or fix the key file, then restart. It never shows the store's own error, which can contain secrets.
- **Locked after start:** nothing changes for the running process. Stop Raphie to release the key; it will not start again until the store is unlocked.
- **Key deleted:** Raphie never creates a replacement for a database that already has encrypted credentials. Restore the key from its backup.
- **Key lost for good:** the encrypted credentials cannot be recovered, and the runtime will not start against those databases. There is no built-in way to discard them and enter the keys again.

## Changing and removing credentials

Editing a key replaces its ciphertext; the connection keeps its identity, so defaults and session choices still point at it. Removing a key deletes its ciphertext from the current database, with SQLite's secure delete on.

:::caution[Removing is not erasing]
An older encrypted backup plus its matching master key can still recover a removed credential. If a key must stop working, revoke or rotate it at the provider.
:::

Upgrades encrypt any older plaintext settings in one transaction before the runtime serves anything. The migration makes no plaintext backup. Never run an older Raphie version against an upgraded database. Stop other runtimes that use the same data directory before you upgrade.

Do not bulk-delete entries under `com.raphie.provider-credentials` in your keychain. Other installations or backups may depend on them.

## Backups

<Steps>

1. Back up the data directory as usual. See [backup and recovery](/operate/backup-and-recovery/).

2. Back up the master key separately: through your OS's own keychain backup, or by copying the headless key file with owner-only permissions to a different place.

3. To restore on a new machine or account, restore both. An encrypted backup is useless without its matching key.

</Steps>

Never store an exported master key beside the database. Backups, archives and journal copies made before encryption still hold plaintext keys: Raphie does not search for or delete them. Protect them, or rotate the provider keys they contain.

## Threats covered

| Covered                                                        | Not covered                                                                                   |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Reading the settings database with SQL tools                   | Other processes running as the same user, which can use the same store or control the runtime |
| Copying the data directory or a database-only backup           | Reading the runtime's memory, or modifying its code                                           |
| Plaintext keys in browser responses, Activity, errors and logs | Root or administrator compromise                                                              |
| Other local users, through `0600` files and `0700` directories | Offline disk theft; use FileVault or full-disk encryption                                     |
|                                                                | Copies kept by SSD wear levelling, snapshots, swap or crash dumps                             |

Stronger isolation would need a separately signed credential broker or a remote secret service. Raphie does not include one.

## Subscription connections

Some providers let you connect with your existing subscription instead of an API key. Raphie offers **Sign in with ChatGPT** for OpenAI.

<Steps>

1. Open **Settings → Providers** and choose the provider's sign-in option.

2. Follow what the sign-in shows: a page to open, or a code to enter.

3. If Raphie runs on another machine, the final page of the browser sign-in will not load, because it returns to `127.0.0.1` on the Raphie machine. Copy that page's address and paste it into Raphie.

</Steps>

| Behaviour                  | Detail                                                                              |
| -------------------------- | ----------------------------------------------------------------------------------- |
| Token storage              | Encrypted like API keys; never sent to a browser, conversation or log               |
| Pasted addresses and codes | Treated as secrets: redacted from logs and never returned in a response             |
| Renewal                    | A token within five minutes of expiry is renewed before the next request and saved  |
| Failed renewal             | The connection shows **Sign in again**; signing in keeps the same connection        |
| Timeout                    | An unfinished sign-in is abandoned after 15 minutes                                 |
| Concurrency                | One sign-in at a time per runtime, because OpenAI's browser sign-in needs port 1455 |
