**Status:** Accepted and in effect.

## Context

One self-hosted runtime should host several assistants, each with its own personality, tools, memory and files, without running a process or VM per idle assistant. Conversations of the same assistant need continuity: files one session creates should be there for the next. At the same time, model-chosen tool arguments must never be able to reach another assistant's data.

## Decision

- A **bot** is the ownership boundary for configuration, sessions, memory scope, workspace and permitted tools. It is not a separate process, VM or user account; the owner remains the only human actor.
- The runtime derives the bot from authorized session or channel ownership, never from tool arguments. Reads, observations, approvals, memory and file operations are authorized against that ownership.
- Each bot has one persistent **workspace** shared by all its sessions. Execution is serialized per workspace; different bots run concurrently within runtime-wide budgets.
- The workspace outlives any **sandbox**. Files cross execution providers through checkpoints and transfer; processes and memory never migrate implicitly.
- Interrupted work with an unknown external outcome stays uncertain and is never replayed. A replaced executor is fenced so it cannot write after a newer one starts.

## Consequences

- `BotHost` opens a separate harness, actor authority, settings, memory, MCP, channel and workspace store per bot inside one process. The default bot keeps the original data layout; named bots live under `bots/<id>/`. See [state](/architecture/state/).
- The workspace presents one file namespace across providers. Uploaded originals are kept separately and content-addressed, so editing a working copy never changes history.
- Credentials and capabilities are resolved only for the authorized bot. There is no cross-bot file or memory sharing operation.
- Separation is logical, not an OS security boundary. Bots share the process, OS user and network; stronger isolation means choosing a stronger sandbox per bot (see [ADR 0003](/decisions/0003-native-bot-sandbox/)).
- Temporary VM leases, named in the original decision as a later execution tier, do not exist. The two providers today are just-bash and an opt-in container.
