**Status:** Accepted and in effect.

## Context

Raphie is reached through very different interfaces: a web workspace, a native desktop client, and messaging channels such as Discord and Telegram. If each interface carried its own copy of the conversation and approval rules, behaviour and crash recovery would drift between them, and each new adapter would inherit fields specific to the first one (such as Discord thread IDs on sessions).

Channels also cannot present everything a rich client can. Discord or Telegram should not need to reproduce the web workspace's activity, usage and diagnostics views.

## Decision

- One self-hosted runtime process owns sessions, turns, tool execution, approvals and delivery records. It is a modular monolith with a single owner of its durable store.
- Clients and channels call a small set of shared application operations: submit a message, decide an approval, control a turn, and focused reads and observations. There is no generic command bus and no per-adapter copy of the rules.
- Sessions have transport-independent identity (public UUIDs). Channel bindings and reply destinations are separate records, not session fields.
- Adapters establish identity and receive a runtime-issued actor context; a caller's JSON never grants authority.
- Capabilities differ by interface. Activity, usage and diagnostics inspection belong to clients that can show them; channels deliver replies and approval cards.

## Consequences

- The runtime works with no web host running. Clients disconnecting never cancels work. See [HTTP API](/architecture/http-api/).
- Channel ingress and client ingress are deliberately different seams: a channel message resolves its own binding and can never name an arbitrary session.
- Every interface shares the same recovery guarantees, described in [execution](/architecture/execution/).
- Continuing a web session from a channel conversation (session linking) is not supported; each channel conversation keeps its own session.
- The runtime port has no credential of its own, so remote access must go through the authenticated web host.
